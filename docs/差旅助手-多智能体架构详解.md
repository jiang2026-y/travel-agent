# 差旅助手多智能体架构详解

> 本文档是对 `travel-agent` 项目的架构深挖笔记，覆盖意图识别、主智能体、三个子智能体、
> 中间件钩子链、记忆分层、HITL 与断点续跑，以及与 Java 参考实现的差异对比。
>
> 所有结论均来自仓库当前代码；标注"未接入 / 占位"的能力表示尚未实现，不要当作已交付能力陈述。
> 偏面试问答口径的速答版见 `docs/面试备考.md`，本文是它的展开与依据。

## 一、项目全景

### 1.1 定位与硬约束

面向企业差旅场景的多智能体助手：用户用自然语言完成差旅申请与审批、机票火车酒店查询预订、
差旅政策与目的地问答。三条硬约束决定了全部技术选择：

1. **写操作不可逆** —— 下单、改单、取消必须由用户确认；
2. **过程必须可见** —— 每一步都要能解释给用户和审计；
3. **外部能力必须可降级** —— 供应商、模型、知识库任何一个不可用，主流程不能中断。

### 1.2 五个运行单元与两个中间件

| 单元 | 职责 | 对外暴露 |
| --- | --- | --- |
| `web` | 对话界面、执行时间线、结果卡片、偏好与管理面板 | 是 |
| `api-server` | 会话与 Run 生命周期、差旅单与审批持久化、偏好、审计、SSE 转发 | 是 |
| `agent-server` | 多智能体编排、工具实现、HITL 与中断、记忆与摘要、事件发布 | 仅内网 |
| `tool-gateway` | 模型与工具出口，按「模型 × Agent」白名单放行 | 仅内网 |
| `egress-proxy` | Squid 出网代理，默认拒绝，仅放行域名白名单 | 仅内网 |
| PostgreSQL 16 | 会话、消息、差旅单、审批、偏好、审计等业务事实 | 仅内网 |
| Redis 8 | LangGraph 检查点、确认 Token 哈希、熔断状态、事件流、中断广播 | 仅内网 |

**拆分的本质是信任边界**，不是"微服务好看"：

- 浏览器只能访问 `api-server`；
- `agent-server` 与 `tool-gateway` 不对公网暴露；
- 模型与第三方调用全部收敛到 `tool-gateway` 唯一出口，出网再由 Squid 兜一道域名白名单；
- 凭据以 Docker Secret 只读挂载到需要的服务——`agent-server` **不持有模型与百炼凭据**。

### 1.3 一次请求的完整链路

```
浏览器
  │ Cookie 会话 + CSRF
  ▼
api-server ── 加密落库用户消息、创建 Run、取脱敏上下文摘要
  │ 内部命令（Bearer Token + 调用链标识校验）
  ▼
agent-server
  ├─ 意图识别：L0 → L1 → L2 →（一次改写）→ L3
  ├─ 路由转换：DIRECT_DISPATCH 或 CLARIFY
  └─ Master Agent（LangGraph ReAct）
        └─ 工具调用 → SubAgentProvider → 子 Agent 独立图
              └─ 工具 → 内部 API / Tool Gateway
  │ SSE 事件流
  ▼
前端执行时间线
```

## 二、意图识别

### 2.1 为什么分四层

成本、延迟与可控性的三角权衡：L1 正则零成本高精度但召回有限；L2 向量覆盖广但有误判风险；
L3 大模型最准也最贵。**短路流程让多数请求在前两层解决，只有不确定的才付模型费用**。

### 2.2 完整流程

```
原始问题
  ├─ L0 强连词守卫 ──命中──▶ 直接进 L3（不改写）
  ├─ L1 规则匹配
  │     ├─ HIT       ──▶ 直接出结果（不改写，不进 L2/L3）
  │     ├─ AMBIGUOUS ──▶ 直接进 L3（不改写，跳过 L2）
  │     └─ MISS      ──▶ 进入 L2
  ├─ L2 向量检索
  │     ├─ 命中      ──▶ 直接出结果
  │     ├─ 歧义      ──▶ 直接进 L3（不改写）
  │     └─ 未命中    ──▶ 允许改写
  ├─ 问题改写（最多一次，脱敏输入）
  │     └─ 用改写后文本重跑 L0/L1/L2（可能命中，省掉 L3）
  └─ L3 模型判定（严格 JSON）
        └─ 失败/未配置 ──▶ `_unknown()` 兜底
```

**关键设计：只有"普通未命中"才允许改写。** 歧义与多意图场景坚决不改写——因为改写会把原句
换成另一种表达，可能把造成歧义的信息抹掉。

### 2.3 L0 强连词守卫

判定条件（同时满足）：

- 句长 ≥ 10
- 句中出现强连词（然后 / 接着 / 顺便 / 顺带 / 以及 / 并且 / 另外 / 同时 / 完了再 / 之后再 / 再帮我 / 再给我 / 外加）
- 连词起始位置 ≥ 4（排除句首衔接词）

命中即判定"疑似多意图复合句"，跳过 L1/L2 直接交给 L3。误判的代价只是走一次慢路径，
不会路由错误。

### 2.4 L1 规则匹配

- 规则来自版本化 YAML（`intent_rules.yml`），**文件顺序即优先级**；
- 每条规则包含 `intent`、正向正则 `pattern` 和可选排除正则 `exclude_pattern`；
- 三种结果：`HIT` / `MISS` / `AMBIGUOUS`；
- `AMBIGUOUS` 有两个触发路径：连词守卫命中，或按分隔符切出的子句识别出 ≥ 2 个意图；
- 特殊规则 `_NON_FINAL_COMPOUND_ACTION`（形如"规划…行程…订…酒店"）返回
  `miss(requires_rewrite=True)`，**强制先改写**；
- 规则里的 `intent_code` 在**启动期**用目录白名单校验，写了不存在的意图会导致服务启动失败。

### 2.5 L2 向量检索

- 独立的 1024 维内存索引，**与景点/政策 RAG 完全隔离**；
- 维度硬校验：不是 1024 直接拒绝，防止换模型后维度不匹配导致静默算错；
- 启动期灌库，每批 10 条调用 `embed_many`；若接入方没有批量能力，则退回逐条 `embed`；
  **灌库失败不替换旧索引**（先攒 `staged` 列表，全部校验通过才赋值）；
- 灌库时校验：意图在目录、向量维度、数值有限（防 NaN/Inf）、**版本必须单一**；
- 检索为暴力全量余弦，**底层不做阈值过滤**——阈值裁决交给上层，便于独立调整与测试。

判定规则（三条同时考虑）：

1. Top-1 分数 ≥ 0.75；
2. 必须存在 Top-2（`top_k=3` 检索，只召回一条也算未命中）；
3. **仅当 Top-2 与 Top-1 属于不同意图、且分差 ≤ 0.05 时，判为歧义**。

> 最容易答错的一点：**Top-2 与 Top-1 是同一意图时，分差多大都算命中。**
> 同一意图的多个不同表达同时排在最前，属于"冗余一致"，比单条命中更可信。

置信度换算：向量分数 ≥ 0.85 为 `high`，0.75–0.85 为 `medium`。而路由要求 `high`，
所以 **0.75–0.85 这段"命中但不直达"**，会被判为 `CLARIFY` 交给主智能体澄清。

### 2.6 问题改写

**触发条件极窄**，只有两类：

1. L1 与 L2 **双双普通未命中**（或 L2 未配置）；
2. 复合动作被 `_NON_FINAL_COMPOUND_ACTION` 拦截——此时 L2 以 `allow_direct_hit=False` 调用，
   **即使向量命中也会被压成未命中**，理由是 `compound_action_requires_rewrite`。

`allow_direct_hit=False` 的设计意图：这类句子确实能被向量识别，但它包含**两个有依赖关系的意图**。
若让 L2 直接单意图命中，用户的第二个诉求会被丢掉。所以宁可放弃这次高分命中，也要先改写，
再由多意图检测或 L3 输出完整意图列表。这与"宁可错过，不可误判"是同一个价值取向。

改写本身的工程约束：

- **输入脱敏**：当前问题与历史都先过 `mask_text`；历史来自 api-server 生成的脱敏摘要
  （最近 10 条 + 脱敏 + 截断 2000 字符）；
- **只允许一次**，改写后必须重跑 L0/L1/L2（改写后即使文本未变化也要重跑，测试专门锁定该行为）；
- **输出校验**：剥 JSON 代码块 → 取 `rewritten_question` → 非空 → 长度 ≤ 8000；
- **失败即降级**：任何异常都被吞掉，`rewrite_status=failed_or_empty`，用原文继续走 L3——
  改写是提升命中率的优化手段，不能成为单点故障；
- **动作词保真**：提示词明确禁止把"申请出差"润色成"安排行程"、禁止给实体追加名词后缀，
  因为下游意图识别对动作动词高度敏感，改一个动词就会路由到不同子智能体。

### 2.7 L3 模型判定与三道校验

L3 返回严格 JSON，依次经过：

1. **解析**：`parse_model_json` 先剥掉 Markdown 代码块标记（三个反引号包裹），再 `json.loads`；
2. **结构校验**（`L3ModelResponse`，`extra="forbid"`）：
   `intents` 长度 1–16；`primary_intent` 必须出现在 `intents` 中；
   `multi_intent` 必须等于 `len(intents) > 1`；`overall_reason` 不得含内部名词；
3. **逐意图校验**（`RecognizedIntent`）：
   `get_intent_definition(intent)` 查目录白名单，查不到抛 `intent_code_not_allowlisted`；
   `target_agent` 必须等于目录声明的值，否则抛 `intent_target_agent_mapping_invalid`；
   `reason` 不得包含内部名词（`bookingAgent`、`target_agent`、`primary_intent` 等）。

三层实际上在一次 `model_validate` 内完成（外层模型构造时会顺带构造内层意图）。

**任何一步失败都被 `_classify_l3` 的 `except Exception` 吞掉，返回 `None`，最终走 `_unknown()`**：
`intent=unknown`、`target_agent=masterAgent`、`confidence=low`。用户看不到报错，只会被多问一句。

注意区分两条都产出 `unknown` 的路径：

| 路径 | 含义 |
| --- | --- |
| L3 **主动**返回 `{"intent": "unknown"}` 且通过校验 | 模型认为信息不足 |
| L3 调用失败 / JSON 非法 / 校验被拒 → `_unknown()` | 系统没拿到有效回答 |

`_unknown()` 只有一个调用点：整条链走完、L3 仍未产出结果时。**L1/L2 命中过就不会走到这里。**

### 2.8 路由转换：四道闸门

`route_from_recognition` 只取 `intents[0]`，四条里任意一条成立即降级为澄清：

1. `multi_intent == True`
2. `confidence != high`
3. `intent == unknown`
4. `target_agent == itineraryPlanAgent`（**意图合法但能力未接入**）

全部满足才 `DIRECT_DISPATCH`，目标直接取 `recognized.target_agent`（此时已被目录校验保证正确）。

> 要诚实的边界：首轮请求即使判定 `DIRECT_DISPATCH`，代码仍然调用主智能体
> （`_stream_master_reply` 无条件执行）。route 的实际作用是持久化状态、发子智能体事件、
> 以及 quick-action 续跑时直接调用子智能体。被硬约束的是"路由声明合法"和
> "主智能体可见的子智能体只有三个"，而不是"代码强制主智能体只能调意图指定的那一个"。

### 2.9 契约测试

两份东西必须逐行一致：

- 提示词 `l3_intent_recognition.md` 里的 Markdown 表格（16 行「意图 → target_agent」）；
- 代码 `INTENT_CATALOG`（16 条，唯一真源）。

测试解析提示词表格，断言与目录完全相等。**防的是"改了一边忘另一边"**：目录改了提示词没改，
模型会照提示词输出旧值，校验器再拒绝，表现为静默降级，线上极难排查。

### 2.10 诊断体系

每一步都写入 `diagnostics`：

| 键 | 内容 |
| --- | --- |
| `l0` | `multi` / `single` |
| `l1` | `hit` / `miss` / `ambiguous` |
| `l2` | `status`、`top1_intent`、`top1_score`、`threshold`、`top2_intent`、`top2_score`、`margin` |
| 改写 | `rewrite_called`、`rewrite_changed`、`rewrite_status` |
| `final` | `source`、`multi_intent`、`intents` |

线上排查"识别错了"的路径：先看 `source` 判断是规则、向量还是模型；若是向量，再看 top1/top2
与分差，判断是阈值问题还是种子库缺样本。

### 2.11 失败语义与保存位置

失败分两级，处理方式完全不同：

| 层级 | 例子 | 处理 |
| --- | --- | --- |
| Provider 级 | L2 检索异常、L3 超时或 JSON 非法 | **降级**：返回 `None` 继续往下，或 `_unknown()` |
| 编排级 | 意图识别整体抛异常 | **整轮失败**：发 `run_error`（`stage=intent_recognition`），Run 置 `FAILED` |

单点能力不可用不该让整轮请求挂掉；但编排层崩溃说明系统有问题，必须显式标记失败。

保存位置：

- 意图识别结果**不落 PostgreSQL**，它只活在"本轮模型上下文"里；
- 路由摘要（`RunRoute`）与诊断事件写在 Redis，随检查点 TTL 过期；
- 用户原始消息加密落 PostgreSQL。

## 三、主智能体

### 3.1 定位

**执行协调者，不是路由器，也不是干活的。** 它不做意图识别、不做业务逻辑，
只做四件事：选工具、转交任务、转发中断、透传结果。

模型为 `qwen3.7-plus`（关闭思考），最大 15 轮推理。

### 3.2 输入契约

每次调用，系统往消息列表里放三条：

```
system: 改写后的问题：<rewritten_question>
system: 意图识别 JSON：<IntentRecognitionResult 完整序列化>
user  : <用户原始问题>
```

- 改写文本用于**理解语义**（指代已消除、实体已补齐）；
- 原始文本保留**用户真实措辞**，作为"用户到底说了什么"的事实基准；
- 意图 JSON 含 `intents`、`primary_intent`、`multi_intent`、`source`、`confidence`、`reason`
  以及 `diagnostics`（调试字段会一并进入模型上下文）。

### 3.3 工具箱（最多 6 个）

| 工具 | 来源 | 说明 |
| --- | --- | --- |
| `ask_user` | 手工注册 | **只有主智能体有**，子智能体都没有 |
| `itinerary_manage_agent` | 动态生成 | 名字即配置 key |
| `booking_agent` | 动态生成 | 同上 |
| `info_agent` | 动态生成 | 同上 |
| `record_to_memory` | 手工注册，**条件性** | 长期记忆写入 |
| `retrieve_from_memory` | 手工注册，**条件性** | 长期记忆召回 |

两点必须说清：

- 三个子智能体工具是**动态生成**的，由 `provider.enabled_configs` 驱动，不是硬编码；
  `enabled=False` 的配置（行程规划、行程审核）不会变成工具；
- 记忆工具**只在配置了长期记忆客户端时注册**——未配置时主智能体只有 4 个工具。

子智能体工具的签名固定为 `(message: str, session_id: str | None)`。

### 3.4 子智能体注册机制

```python
agent_key = (request.context.user_id, request.context.thread_id)
agent = agent_holder.get(agent_key)
if agent is None:
    agent = cls._create_sub_agent(...)   # 首次调用才创建
    agent_holder[agent_key] = agent
```

- **懒加载**：启动时不实例化任何子智能体；
- **缓存键为 `(user_id, thread_id)`**：不同用户绝不共用实例；
- 同一会话内复用实例，因此 `SessionCtx` 中的工具缓存（政策、档案完整度、常驻地）会累积。

`session_id` 约定：首次调用不传（自动生成 `{thread_id}:{agent_key}`）；同一轮内追问可传上次的值
复用短时记忆；跨轮不依赖子智能体记忆。

### 3.5 中间件链

```
熔断（awrap_tool_call）
→ 技能正文折叠 / Token 统计（awrap_model_call）+ 工具结果压缩（awrap_tool_call）
→ 工具进度事件（awrap_tool_call）
→ 错误转译（aon_error）
→ 摘要（before_model，可选）
→ 调用上限（before_model + after_model）
```

主智能体**没有**动态时间注入（不做日期推理，相对日期交给子智能体），
也**没有** HITL 中间件（自己不执行写操作）。

### 3.6 中断跨层转发

子智能体的中断发生在**子图**里，但挂起必须发生在**主图**上，中间靠四跳接力：

```
① 子图内：HITL 中间件拦下写工具 → 抛 interrupt → 子图挂起，输出含 __interrupt__
② SubAgentProvider 抽取：_extract_pending_interaction 兼容两种形状
     · ask_user 的显式载荷（带 kind）
     · HITL 中间件的 action_requests → 归一为 {kind:"approval", action:{tool_name, tool_args}}
③ 主智能体转发：if result.pending_interaction is not None: interrupt(...)  ← 在主图再次中断
④ 服务层签发：生成 interaction_id、记录 args_hash、存 Redis（只存 token 哈希）→ 前端弹卡
```

**中断不会自动冒泡**，是靠 `call_sub_agent` 里那一行显式转交的。

### 3.7 恢复与防误判

```python
if (request.resume_value is not None
    and hasattr(agent, "aresume")
    and await _has_pending_interrupt(agent, session_id)):
    result = await agent.aresume(...)     # 确认停在中断上，才用恢复值
else:
    result = await agent.ainvoke(...)
```

**为什么必须检查**：恢复值挂在 ContextVar 上，整个恢复过程都在。若主图恢复后调用了
**另一个**子智能体，那个子智能体从未中断过，却会拿到上一条恢复值——它会把它当成新指令，
重跑并重复提问。

### 3.8 结果透传三原则

提示词里的硬约束，本质是**对抗 LLM 当二传手时的默认毛病**：

1. **原样透传**：优先直接把子智能体回复给用户，禁止用自己生成的回复覆盖或替代；
   待确认内容（事由、城市、日期、原始确认问句）必须完整保留，禁止简化为"是否确认？"；
2. **不得预判结果**：子智能体返回前，禁止声称"已提交 / 已完成 / 已取消"；
3. **原样转发用户确认**：用户只回"确定"这类短句时，必须把原话放进 message
   （例如 `用户确认：确定`），不要改写成一段需求描述，否则子智能体会以为要重走流程。

### 3.9 记忆分层

| 层 | 载体 | 隔离维度 | 说明 |
| --- | --- | --- | --- |
| ① 本轮输入 | 消息列表 | 单次请求 | 三条消息，用完即弃 |
| ② 会话短期 | LangGraph checkpointer（Redis） | `thread_id` | **整张图的状态**，图自动存取 |
| ③ 压缩摘要 | 同一份图状态内 | `thread_id` | 超阈值时把老消息替换成一条摘要消息 |
| ④ 长期偏好 | 百炼记忆库（经 Tool Gateway） | `user_id` | 两个工具显式调用 |

三个容易答错的点：

- checkpointer 存的是**整张图的状态**，"意图识别 JSON"只是其中一条 system 消息，没有独立存储；
- 摘要是**改写消息列表**，不是单独存到别处的另一个对象；
- **`context_summary` 不传给主智能体**——它只喂问题改写、L3 判定与推荐问题生成。

### 3.10 边界

不重新识别意图、不重新改写问题、不直接操作数据库、不直接调外部 API、
不自己回答业务问题、不向用户暴露内部名称。

## 四、三个子智能体

### 4.1 统一骨架

三个都是同一模式：`create_agent` 构建的**独立 LangGraph 图**，各自有
`{主线程id}:{agent_key}` 形式的线程号，共享同一个 Redis checkpointer 实例但按 thread 隔离。

共同点：不直接对用户说话；只接收主智能体转交的自然语言任务；不做意图识别；
挂同一套中间件（可选件不同）。

### 4.2 对比总表

| | `itineraryManageAgent` | `bookingAgent` | `infoAgent` |
| --- | --- | --- | --- |
| 模型 | qwen3.7-plus | qwen3.7-plus | **glm-5.1** |
| 迭代上限 | 10 | 10 | **5** |
| 工具数 | 18 | 26 | 11 |
| 职责 | 差旅单全生命周期 | 实时查询 + 预订执行 | 只读信息查询 |
| 写操作 | 提交 / 取消 / 修改差旅单 | 下单 / 取消预订 | 无 |
| HITL | 4 个写工具 | 4 个写工具（仅途牛启用时挂载） | 无 |
| 结果卡片 | 无 | 3 个查询工具 | 无 |
| 技能工具 | 无 | 懒加载 + 受控 shell | 无 |

迭代上限与模型分档的依据：信息查询是"查一次、答一句"，5 轮足够；
行程与预订要"收集 → 校验 → 提交"，需要 10 轮。

### 4.3 itineraryManageAgent

工具分七组：

| 组 | 数量 | 工具 |
| --- | --- | --- |
| 差旅单写（HITL） | 3 | `submit_travel_approval`、`cancel_travel_order`、`modify_travel_order` |
| 冲突检查 | 1 | `check_travel_order_conflicts` |
| 差旅单只读 | 6 | `query_travel_order`、`..._by_order_id`、`query_travel_orders`、`query_approval_status`、`check_travel_order_approval`、`check_travel_time_validity` |
| 预订只读 | 1 | `query_booking_record` |
| 预订写（HITL） | 1 | `cancel_booking`（内部记录，外部 Provider 由 API 层拒绝） |
| 政策 | 2 | `query_travel_policy`、`check_travel_policy` |
| 用户档案 | 4 | `query/update_user_contact_info`、`query/update_user_base_location` |

提交流程的关键约束：

1. 缺出发城市时先 `query_user_base_location()` 取常驻地作默认；
2. **发起新差旅前必须调 `check_travel_order_conflicts`**：
   HIGH 冲突必须先展示明细并取得用户明确同意；MEDIUM 由用户决定；LOW 一句话提示；
3. 信息完整后**直接调用 `submit_travel_approval`**，由工具触发前端确认卡片——
   **禁止用纯文字再问一遍"是否确认提交"**；
4. 用户只回确认词时，立即提交，禁止重复查冲突或重复索要信息；
5. 单号不需要自己编造，系统会自动生成。

取消与修改的关键约束：

- 取消 APPROVED 单据会返回二次确认警告，需说明影响后再调用；
- **修改涉及日期或城市时，必须重新跑冲突检查**，并传 `exclude_order_id = 当前单据`
  避免与自身冲突；
- 取消/修改成功后，工具会返回关联预订列表，**必须提示用户**有哪些预订尚未取消；
  但**无权取消外部预订**，只能引导用户说"帮我取消这些预订"，由预订服务接手——见 4.7。

其他实现细节：

- **日期归一化**：`TravelDateNormalizer` 把"下周三""本月底""十号"等表达统一解析为
  `Asia/Shanghai` 业务日历下的 ISO 日期，内置可替换时钟保证测试可重复；
- **幂等**：提交前先按 `order_id` 查重，命中即返回原结果；单号**不放进请求体**，
  避免破坏确认时生成的参数指纹；服务端另有按"目的地 + 出发城市 + 出发日期 + 返回日期 + 事由"
  的去重（状态只考虑 DRAFT/SUBMITTED/APPROVED）；
- **冲突规则不在 Agent 侧**：工具只转发，真正的规则引擎在 api-server，是纯函数、可脱离
  数据库单测——五条规则按优先级逐条判定，每条已有行程最多命中一个分支；
- **会话级工具缓存**：政策 JSON（按城市）、档案完整度摘要、常驻地会缓存，
  用 `asyncio.Lock` 协调并发回源；动态校验类结果不缓存。

### 4.4 bookingAgent

工具分七组：差旅单只读 6 + 预订只读 1 + 用户档案 4 + API Key 4 + 技能 2 + 途牛业务 7。

两个其他子智能体都没有的机制：

**① 技能懒加载 + 受控 shell**

- `load_skill_through_path` 按需加载技能正文（如 `tuniu-cli`）；
- `execute_shell_command` 只在白名单内执行：命令首词仅限
  `tuniu/bash/cat/grep/date/which/ls`，路径必须位于技能目录内，
  **禁止选项、管道、重定向与命令串联**，并显式拒绝包含 `/run/secrets` 的命令。

**② 写操作前的两道强制校验**

- **审批检查**：下单前必须调 `check_travel_order_approval`；
  返回 `approved=false` 时**直接拒绝预订**，不得以任何理由绕过；
- **防重复预订**：下单前先 `query_booking_record` 检查是否已有相同行程的预订。

查询与下单的边界也写得很清楚：**查询不需要差旅单，也不需要审批校验**；
只有写操作才需要用户明确确认。

### 4.5 infoAgent

工具分四组：知识库检索 1 + 政策 2 + 天气/资讯 2 + 签证 6。纯只读，无 HITL。

提示词里最有设计感的是**政策双通道**，且明确"严禁混用"：

| 通道 | 适用场景 | 工具 |
| --- | --- | --- |
| 知识库（RAG） | 通用规则类问题（"差旅制度对超标住宿怎么规定"） | `retrieve_knowledge` |
| 政策工具 | **与用户身份绑定的精确数据**（"我去 X 城市的住宿标准"） | `query_travel_policy` / `check_travel_policy` |

原因是 RAG 召回的是通用语义，用来回答"我的标准是多少"会给出不准确的数字。

### 4.6 写操作前的两条业务红线

| 子智能体 | 前置校验 | 不通过的结果 |
| --- | --- | --- |
| itineraryManage | **冲突检查** | HIGH 冲突需用户明确同意才能继续 |
| booking | **审批检查** | `approved=false` → 直接拒绝，无协商余地 |

注意两者的**性质不同**：冲突检查是"提示风险、由用户决定"，审批检查是"硬性拒绝"。
两条红线都落在**工具返回的事实**上，而不是靠模型自由判断。

### 4.7 子智能体之间如何协作

**子智能体之间没有任何直接通道**——它们互不认识，唯一能调度它们的是主智能体的工具调用。
跨 Agent 协作只有两条路径：

| 路径 | 机制 |
| --- | --- |
| 同一轮内 | 意图识别输出 `multi_intent=true`，主智能体按 `intents` 数组**顺序依次调用** |
| 新一轮 | 用户**再发一句话**，触发全新的意图识别与路由 |

"取消差旅单后处理关联预订"走的是第二条：行程管理子智能体只**提示**用户，不代劳。

**为什么不让主智能体自动串起来**：取消预订是破坏性操作，用户这一轮说的是"取消出差"，
并没有说"取消机票"。自动串联等于擅自扩大用户授权范围。原则是：
**读操作可以自动串联，写操作必须由用户显式发起。**

## 五、中间件与钩子链

### 5.1 两个盒子

一个 Agent 每轮只做两件事：**调模型**、**调工具**。中间件就是套在这两个动作外面的处理层。

```
模型盒子：技能折叠 → Token 统计 →（时间注入）→ 摘要 → 【模型】
工具盒子：熔断 → 结果压缩 → 进度事件 → 结果卡片 → HITL → 【真实工具】
```

**是包裹（洋葱），不是排队**：进的时候从外往里，出的时候从里往外。同一层可以只管进门、
只管出门、或两头都管。

### 5.2 钩子的两种落地形态（实测）

用项目里真实的中间件编译出图，看节点列表：

| 中间件 | 编译后新增的节点 |
| --- | --- |
| 无 | `['model']` |
| `DynamicTimeInjectionHook` | `['model', 'DynamicTimeInjectionHook.before_model']` |
| `SummarizationMiddleware` | `['model', 'SummarizationMiddleware.before_model']` |
| `HumanInTheLoopMiddleware` | `['model', 'HumanInTheLoopMiddleware.after_model']` |
| `ModelCallLimitMiddleware` | `['model', '...before_model', '...after_model']` |
| `ToolErrorMiddleware` | `['model', 'tools']`（**无新增**） |
| 任意 `wrap_model_call` / `wrap_tool_call` | **无新增** |

结论：

- `before_model` / `after_model` 钩子会被**编译成独立图节点**，命名规则为 `{中间件类名}.{钩子名}`；
- `wrap_*` 钩子**不生成节点**，而是包裹在 `model` / `tools` 节点内部执行；
- 基础图骨架固定为 `__start__ → model → tools →（循环）→ __end__`。

LangChain 源码中的规则是：**列表里第一个是最外层**（"compose with first in list as outermost layer"）。

### 5.3 顺序的意义

- **熔断必须在最外层**：一旦打开就直接返回降级消息，后面的层根本不执行（不压缩、不发事件、不调工具）；
- **HITL 必须在最内层**：紧贴真实执行点，避免"进度事件已经发了、结果卡片已经生成了，
  然后突然要等用户确认"；
- **中断信号必须穿过所有层**：熔断里显式区分控制流信号，遇到 `interrupt` 直接 `raise`，
  不记失败；`ToolErrorMiddleware` 也不会拦截中断。

### 5.4 各 Agent 的实际链

| Agent | 组成 |
| --- | --- |
| `masterAgent` | 熔断 → 技能折叠/Token/结果压缩 → 进度 → 错误转译 → 摘要 → 调用上限（15） |
| `itineraryManageAgent` | 熔断 → 上下文效率 → 进度 → **时间注入** → 错误转译 → 摘要 → **HITL** → 调用上限（10） |
| `bookingAgent` | 熔断 → 上下文效率 → 进度 → **结果卡片** → **时间注入** → 错误转译 → 摘要 → **HITL**（条件） → 调用上限（10） |
| `infoAgent` | 熔断 → 上下文效率 → 进度 → **时间注入** → 错误转译 → 摘要 → 调用上限（5） |

### 5.5 一个可优化点

`DynamicTimeInjectionHook` 里有一个**空实现的 `before_model`**（返回 `None`），
但因为"实现了就建节点"，它会让每个挂了时间注入的 Agent 多出一个什么都不做的图节点，
每次模型调用多走一跳（在挂 checkpointer 的情况下还可能带来额外的状态持久化开销）。
修法是把 `before_model` 删掉，只保留真正的 `awrap_model_call`。

## 六、记忆与存储

### 6.1 四层记忆

见 3.9。核心记忆：**分层维度不同**——短期按 thread、长期按 user、业务事实按 conversation。

### 6.2 谁存哪

| 信息 | 存储位置 | 生命周期 | 消费者 |
| --- | --- | --- | --- |
| 意图识别结果 | 图状态（消息列表内的一条 system 消息） | 随检查点 TTL | 主智能体推理 |
| RunRoute 摘要 | Redis | 随检查点 TTL | 断点续跑、quick-action、状态查询 |
| 诊断事件（32 类） | Redis 事件存储 | 随检查点 TTL | SSE 时间线、管理员诊断 |
| 用户原始消息 | PostgreSQL（AES-256-GCM 加密） | 永久（软删除） | 会话历史、上下文摘要 |
| 长期偏好 | 百炼记忆库（经 Tool Gateway） | 由百炼管理 | 两个记忆工具 |

**意图识别结果不落 PostgreSQL**——它是推理中间产物，不是业务事实。

### 6.3 长期记忆的实现取舍

与参考实现（框架托管、`AGENT_CONTROL` 模式自动注册工具）相比，本项目选择**显式手工实现**：

| 维度 | 框架托管 | 本项目 |
| --- | --- | --- |
| 工具创建 | 框架按模式自动注册 | 项目代码手工注册 |
| 凭据位置 | API Key 注入应用进程 | 只存 Docker Secret，经 Tool Gateway 转发 |
| 写入前处理 | 无 | 强制脱敏 + 截断（写入 2000 / 查询 1000 字符） |
| 缓存 | 有（Redis + 写后失效） | 无 |
| 降级表现 | 未配置返回 `null`，Agent 不自知 | 返回结构化失败结果，模型可告知用户 |

选择理由：**agent-server 不持有任何外部凭据**是这个架构的前提；框架自动模式要求进程内持有
embedding 凭据并绕开网关。代价是样板代码更多、缺一层缓存——缓存可以后补（在网关侧或客户端
前面加一层），但凭据边界一旦定错就要动部署拓扑。

## 七、HITL 与断点续跑

### 7.1 挂起不是等待

| 常见误解 | 事实 |
| --- | --- |
| 后端协程挂在那里等用户 | 中断后**请求正常返回**，协程已结束 |
| 一直在轮询前端 | 前端是"发现有待交互就渲染卡片"，服务端不轮询 |
| 必须马上回复否则超时 | 可以隔几小时，中间重启服务也没关系 |

两次 HTTP 请求之间**没有任何东西活着**，服务端留下的只有 Redis 里的状态快照。

LangGraph 的 `interrupt()` 不是阻塞线程，它做三件事：把状态写进 checkpointer 并标记停在哪；
抛出控制流信号把图整个退出来；`ainvoke` 返回带 `__interrupt__` 的部分状态。下次用**同一个
`thread_id`** 加 `Command(resume=值)` 调用，图从该点重进，并让当时的 `interrupt()` "返回"这个值。

### 7.2 中断转发的四跳

见 3.6。

### 7.3 恢复的七步

```
① 前端 POST /runs/{id}/resume
     body: {kind:"decision", interaction_id, decision:"approve", confirmation_token}
② api-server 鉴权 + CSRF，转内部命令给 agent-server
③ agent-server validate_decision：
     身份四元组（user_id/conversation_id/run_id/thread_id）全匹配
     + decision 在 allowed_decisions 内 + confirmation_token 哈希匹配
④ approve 时 hide_from_display：摘掉展示索引（防恢复期间卡片反复弹），记录与 Token 保留
⑤ 构造 resume_value（两种形状，分别对齐两种中断来源）
     clarification → {"message": ...}                  （ask_user 的 interrupt 返回值）
     approval      → {"decisions": [{"type": "approve"}]}（HITL 中间件内部取 ["decisions"]）
⑥ 绑定工具执行授权（ContextVar，只在本次恢复期间有效，finally 清除）
   → master_agent.aresume(resume_value, thread_id, context)
⑦ Master 用 `Command(resume=)` 恢复主图 → 模型再次调用 call_sub_agent
   → 把 resume_value 塞进 SubAgentRequest → provider 判断"是否真停在中断上"
   → 是则 agent.aresume(...) → 子图重进 → HITL 放行 → 写工具真正执行
```

### 7.4 三条恢复通道

agent-server 收到 `resume` 命令后按字段分流：

| 通道 | 触发条件 | 是否重跑意图识别 | 执行方式 |
| --- | --- | --- | --- |
| 快速操作 | `quick_action` 非空 | 否 | 取 `checkpoint.route.target_agent`，直接 `provider.invoke` |
| 结构化决定 | `resume_decision` 非空 | 否（**edit 除外**） | `master_agent.aresume(...)` 从检查点续跑 |
| 普通消息 | 两者都为空 | **是** | 完整跑 L0–L3，再进主智能体 |

`edit` 是唯一例外：先 reject 原交互，然后**重新跑完整意图识别**——因为"修改"意味着用户给了
新内容，等于新需求。

前端侧还有一个关键分流：有待交互时，用户直接打字"确定"会被 `decisionForText` 翻译成
`decision: approve`（词表：确定/确认/好的/好/可以/同意/提交/是/yes/ok），
走与点按钮**完全相同**的通道，不经过意图识别。只有不在词表里的自由表达才会退化成普通消息。

### 7.5 确认 Token 的五道防护

1. Redis **只存 Token 的 SHA-256**，不存明文；
2. TTL 900 秒，且前端轮询会轮换 Token，服务端保留前一版哈希做**宽限**
   （解决"点击时刚好过期"的竞态）；
3. 绑定**工具参数指纹** `args_hash`，防止确认后替换参数；
4. 写事务执行前用 `WATCH/MULTI` **原子消费** Token，并把交互标识作为幂等键；
5. 用户提交决定后立即**摘除展示索引**（保留记录供消费），避免恢复期间卡片反复弹出。

## 八、与 Java 参考实现的对比

> 参考实现为 AgentScope + Spring 的 Java 版本，本项目是它在 Python 技术栈上的重写与裁剪。

### 8.1 总体结论

**功能定位一致（提示词几乎是同一份：138 行 vs 142 行，95% 相同），实现机制不同，
能力覆盖面 Python 是子集，并主动修正了参考实现的若干问题。**

### 8.2 主 Agent 对比

| 维度 | Java | Python |
| --- | --- | --- |
| 框架 | AgentScope `ReActAgent` + Spring | LangChain `create_agent` + LangGraph |
| 子 Agent 工具 | **4 个**（含行程规划） | **3 个**（行程规划未接入） |
| 记忆工具 | 框架按 `AGENT_CONTROL` 自动注册 | 手工注册、条件性 |
| 工具总数 | 5 | 6（未配长期记忆时 4） |
| 迭代上限 | 15 | 15（一致） |
| 实例生命周期 | Spring `prototype`，每次新建 | 懒加载 + `(user_id, thread_id)` 缓存 |
| 工具执行配置 | 超时 15 分钟 / 重试 3 次 / 退避 3 秒 | 无 per-tool 重试，改用熔断 + 网关超时 |
| 上下文压缩 | `AutoContextMemory`：60 条 / 128K×0.75 / 保留 20 条 + **4KB 大负载卸载** | `SummarizationMiddleware`：60 条 / **98304** token / 保留 20 条 |
| Prompt 缓存 | `cacheControl(true)` | 无 |

三个阈值完全一致（60 条 / 98304 token / 保留 20 条），而 `98304 = 128 × 1024 × 0.75`
正是 Java 侧配置的换算结果——这是 Python 移植自 Java 的直接证据。

提示词差异集中在四处：意图映射（规划与报销在 Python 标注为"未接入"）、
航班火车酒店查询改由预订子智能体承担、新增"不得预判结果"与"原样转发用户确认"两条规则。

### 8.3 行程管理子 Agent 对比

工具数 15（Java）vs 18（Python），差异来自注册位置划分：

| 组 | Java | Python |
| --- | --- | --- |
| 差旅单写 | 3 | 3 |
| 冲突检查 | 1 | 1 |
| 差旅单只读 | 6 | 6 |
| 预订只读 | 1 | 1 |
| 预订写 | 未注册 | 1（`cancel_booking`） |
| 政策 | 未注册 | 2 |
| 用户档案 | 2 + 2（拆两个类） | 4（合并一个类） |

提示词的实质差异：

1. `query_user_base_location(user_id)` → `query_user_base_location()`——
   **身份参数不再由模型提供**，改为服务端从上下文注入；
2. 提交确认方式改变（见 8.4）；
3. 取消工具参数模型变化：Java 用 `force=true` 二次调用，Python 改为重新调用同一工具。

### 8.4 关键差异：写操作确认机制

| | Java | Python |
| --- | --- | --- |
| 谁来保证确认 | **模型**（提示词要求先问用户） | **框架中间件**（执行前强制拦截） |
| 确认载体 | 工具返回值 + `force` 布尔参数 | 前端确认卡 + 一次性 Token |
| 防篡改 | 无 | `args_hash` 绑定工具参数 |
| 幂等 | 工具自身判重 | Token 原子消费 + `idempotency_key` |
| 能否绕过 | **能**——模型自填 `force=true` 即跳过确认 | **不能**——拦截发生在工具执行之前 |

Java 的实现是"工具返回值驱动"：`cancel_travel_order` 遇到 APPROVED 单据且未传 `force` 时
返回 `needConfirm=true`，模型转达用户、用户确认后再带 `force=true` 重新调用。
**`force` 是模型自己填的参数**，提示词里"必须先问用户"是软约束，不遵守也无人拦。

Python 把这道关从提示词搬到了中间件，**模型没有能力绕过**。

### 8.5 Python 版修正的问题

1. 参考实现提示词要求调用 `reimbursement_agent`，但主智能体的 toolkit **并未注册该工具**
   （且 `ReimbursementAgent.build()` 直接 `return null`）。Python 把提示词改为
   "报销能力未接入，不调用任何子智能体"，消除了这个不一致；
2. 写操作确认从软约束改为机制性拦截（见 8.4）；
3. 身份参数改为服务端注入，模型无法伪造 `user_id`。

### 8.6 明确未实现（不要当作已交付能力）

行程规划子智能体、行程审核与仲裁体系、报销子智能体、主观评估 Agent、
大负载卸载（超阈值内容转存）、工具级重试与退避、Prompt 缓存。

## 十、面试陈述纪律

- 只讲代码里真实存在的机制，规划中的能力主动标注"未接入 / 待补"；
- 区分"逻辑模块"与"部署单元"：四个智能体同属一个 `agent-server` 进程，不是四个服务；
- 讲"路由权收回"时要说准：被锁的是**路由声明合法**与**主智能体可见的子智能体只有三个**，
  而不是"代码强制主智能体只能调意图指定的那一个"；
- 讲"直跳子智能体"时要说明：参考实现曾尝试该方案并已回滚，调度统一经过主智能体；
- 工具数量要报口径：网关白名单登记 61 条、去重 45 个名字，README 的 42 是仅统计业务工具。

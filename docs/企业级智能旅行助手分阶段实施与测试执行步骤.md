# 企业级智能旅行助手分阶段实施与测试执行步骤

> 文档职责：将已确认的需求、技术选型、目录结构与 Feature `001-travel-assistant-mvp` 的 94 项任务转化为可顺序执行的开发步骤。每个阶段必须形成“实现 → 自动化测试 → 人工演示 → 验收证据”的闭环，未通过不得进入下一阶段。  
> P0 边界：以《远程工具沙箱与真实只读接入基线》为准。真实只读百炼、远程 HTTP MCP 与 Skill 仅在局部门禁、Provider 白名单和沙箱策略满足后启用；无配置必须拒绝调用。禁止真实订票、支付、改签、取消、退款和报销提交。

**关联基线**：[需求文档](./企业级智能旅行助手需求文档.md)、[技术选型](./企业级智能旅行助手技术选型.md)、[目录结构](./企业级智能旅行助手目录结构.md)、[Feature 任务清单](../specs/001-travel-assistant-mvp/tasks.md)。

## 1. 通用执行规则

### 1.1 每个阶段的闭环定义

每个阶段必须同时满足以下六项，才可标记完成：

1. **范围确认**：已说明本阶段对应的任务、非目标和未解锁门禁。
2. **契约先行**：涉及 REST、SSE 或内部命令时，先更新 Schema/契约测试，再写实现。
3. **测试先行**：任务清单中规定的单元、契约、集成或浏览器测试先编写并确认其在实现前失败。
4. **实现验证**：实现后全部相关自动化测试通过，且不得以跳过、放宽断言或伪造成功规避失败路径。
5. **人工演示**：按本阶段验收场景完成一次可重复演示，记录测试数据、关联标识、结果和失败处理。
6. **证据归档**：在任务清单勾选完成项，并将测试报告、关键 `trace_id` / `run_id`、契约版本和遗留风险写入变更说明或验收记录。

### 1.2 强制安全和日志规则

- 所有 REST、SSE 生命周期、API↔Agent 命令、Agent 节点、模型/记忆/RAG、Skill 与关键数据库边界必须生成带 `trace_id`、`request_id`、`run_id`、`thread_id` 的结构化日志。
- 日志只保存字段白名单、脱敏请求/响应摘要、内容长度/哈希、耗时、状态、错误和重试；禁止记录验证码、Cookie、Token、密钥、证件、完整提示词、私有思维链或未经脱敏的个人文本。
- 每次新增或修改接口，都必须补充成功、鉴权失败、参数错误和依赖失败四类验证；涉及状态变更时还必须验证幂等和 CSRF。
- 所有新建代码文件开头均使用中文注释说明职责，并列出其中函数或类的功能；所有 Markdown 文档使用中文。

## 2. 步骤 0：门禁登记与开发基线确认

**对应任务**：T001。  
**目标**：在任何代码和供应商接入前，建立可审计的开发边界。

1. 阅读需求、技术选型、目录结构、Feature 规格、计划、契约和任务清单。
2. 在 `implementation-gates.md` 为 G1～G9 记录负责人、状态、解锁依据、影响范围和复核日期。
3. 明确 P0 的启用能力均为 Fake 或只读；在界面、API 和日志中对未配置能力显示“Fake / 禁用 / 待配置”，不得伪装成功。

**测试与验收**：

- 文档审查确认 G1～G9 无“默认已确认”的表述。
- 抽查一个真实写 Skill、一个真实百炼配置和一个 DDL 任务，均应处于阻塞状态。
- 输出门禁台账链接和评审记录；通过后才可开始步骤 1。

## 3. 步骤 1：仓库骨架与本地可启动环境

**对应任务**：T002～T008。  
**目标**：建立 Web、API Server、Agent Server、契约包和本地编排，不实现业务功能。

1. 初始化 React 19 + Vite + TypeScript 前端工程，以及两个 Python 3.12 服务包。
2. 创建 `packages/contracts`、质量工具、环境变量样例、密钥忽略规则和本地 `compose` 编排。
3. 确保所有环境变量样例仅包含变量名或 Fake 值，不包含真实百炼、数据库、Redis 或 Skill 凭据。

**测试与验收**：

- 前端执行类型检查、Lint 和生产构建；两个 Python 服务执行导入检查、Ruff、mypy 和空测试集。
- 本地编排能启动 Web、API、Agent、PostgreSQL 与 Redis；健康检查可区分“服务正常”和“外部能力未配置”。
- 扫描仓库，确认没有真实密钥、DDL、迁移或真实供应商地址；保留构建输出和启动日志作为证据。

## 4. 步骤 2：基础契约、安全与可观测性底座

**对应任务**：T009～T020。  
**目标**：在任何用户故事前建立文件规范、Cookie/CSRF、错误信封、关联标识、脱敏日志、Fake Adapter 与跨服务契约。

1. 实现新代码中文文件头检查，并在 CI 或本地质量命令中启用。
2. 定义环境配置、Cookie 属性、CSRF、功能开关、关联标识、字段脱敏和统一错误信封。
3. 将 REST、SSE、API→Agent 命令写为可验证 Schema；Agent 必须二次校验用户和角色。
4. 建立内存 Fake 用户、会话、事件、模型、Skill、检查点和审计 Adapter；定义真实持久化与供应商端口但不实现其生产连接。

**测试与验收**：

- 契约测试验证 Schema 版本、非法字段、未认证访问和敏感字段拒绝。
- 单元测试验证脱敏器不会输出验证码、Cookie、Token、提示词和思维链。
- 集成测试模拟 API→Agent 调用，确认 `trace_id`、`request_id`、`run_id`、`thread_id` 完整透传，失败返回安全错误。
- 人工按一个请求的 `trace_id` 检索日志，确认能看到脱敏时序而不含原文敏感值。

**退出条件**：所有用户故事只能经 API Server 访问 Agent Server；所有跨服务失败均带关联标识和安全错误。

## 5. 步骤 3：US1 账号登录与资源隔离闭环

**对应任务**：T021～T029。  
**目标**：以预置账号测试夹具实现 Cookie 登录、普通用户/管理员、会话退出与受保护工作台。

1. 先编写认证、Cookie/CSRF、错误凭据、跨用户拒绝、角色提升拒绝和浏览器验收测试。
2. 实现预置账号密码登录、`HttpOnly` Cookie、CSRF、退出、会话过期和登录限流。
3. 实现前端登录、工作台保护路由和退出入口；前端不读取或存储令牌。
4. 记录管理员访问、登录失败、退出、会话过期和权限拒绝审计。

**测试与验收**：

- 预置账号使用正确密码可登录；错误凭据统一失败；响应和日志中没有密码、Cookie 或 Token 值。
- 普通用户不能读取其他用户资源，不能自助提升为管理员，且拒绝响应不泄露资源是否存在。
- 管理员可查看授权范围内的脱敏记录，查询行为自身产生审计。

**退出条件**：可独立演示“预置账号登录 → 工作台 → 退出/会话过期 → 受保护资源拒绝”，无需启动真实百炼或旅行 Skill。

## 6. 步骤 4：US2 会话、run 与中断恢复闭环

**对应任务**：T030～T038。  
**目标**：让一次用户输入形成唯一会话和可恢复 run，支持取消、状态查询、检查点、摘要和记忆优先级。

1. 先完成会话/run REST 契约测试、检查点恢复测试、上下文优先级测试。
2. 实现会话/run 端口、幂等请求、稳定 `thread_id`、内存测试检查点和 Redis 检查点适配边界。
3. 实现当前会话确认事实优先于长期记忆、上下文压缩、注销后记忆停止注入。
4. 在前端实现会话列表、创建会话、run 状态查询、取消和恢复入口。

**测试与验收**：

- 新会话首条消息只创建一个 `conversation_id` 和一个 `run_id`。
- 模拟 SSE 断线、Agent 重启、重复 resume 和 Redis 故障；系统显示真实状态，不重复执行已完成步骤。
- 日志可从请求关联到会话、run 和检查点恢复动作。

**退出条件**：可独立演示“创建会话 → 中断 → 重连/查询 → 同一 `thread_id` 恢复”。

## 7. 步骤 5：US3 L0～L3 意图识别闭环

**对应任务**：T039～T048。  
**目标**：实现可测试、可解释、受白名单约束的 L0～L3 识别管线；生产意图目录仍受 G1 约束。

1. 先用固定 Fake 样本编写路径回归、结果校验和性能基准测试。
2. 实现 L0 单/多/不确定判别；明确多意图或不确定直接进入 L3。
3. 实现 L1 句子拆分、规则唯一命中；多个命中进入 L3，无命中进入 L2。
4. 实现 L2 端口及 Fake 向量匹配；只有 Top-1 达阈值、Top-1/Top-2 同意图且分差符合配置才命中。
5. 实现最多一次问题改写、关键约束保护、L3 Fake 结构化识别、统一 `IntentRecognitionResult` 和主控自然语言简报。

**测试与验收**：

- 覆盖规则命中、向量命中、多意图、不确定、未命中、改写后命中和改写后进入 L3。
- 断言 L1/L2 最终命中时 L3 调用次数为零；白名单外 Agent、非法结构和低置信输出安全失败。
- 固定环境下 L0/L1 p95 小于 50ms、L2 p95 小于 100ms；L3 必须先产生阶段事件并记录时延。
- 所有结果可由来源、置信度、规则/样本依据、改写轨迹和关联标识追溯。

**退出条件**：识别管线在 Fake 模型环境可独立回归，且不硬编码未确认的 16 类生产配置。

## 8. 步骤 6：US4 澄清与只读旅行查询闭环

**对应任务**：T049～T060。  
**目标**：实现 Master、子图、澄清、Fake 只读 Skill 与候选方案；不进行真实预订。

1. 先编写主控路由、缺槽位澄清、Skill 并行、候选来源/失效和失败降级测试。
2. 实现工具注册表、只读属性、权限校验和 Fake 航班/酒店等查询工具。
3. 实现澄清节点、候选方案模型、InfoAgent、ItineraryPlanAgent，以及其他子 Agent 的只读/禁用占位能力。
4. 实现 LangGraph 主控与条件路由；仅互不依赖的只读 Skill 可并行，用户可见事件必须稳定排序。
5. 实现候选卡片、澄清卡片、来源、查询时间、假设、限制、冲突和失效展示。

**测试与验收**：

- 缺目的地或日期时一次只提出 1～3 个高价值问题，不直接做最终选择。
- Fake 查询结果必须显示来源、查询时间、版本、限制和待确认项；冲突、过期或字段缺失不能被展示为确定事实。
- 两个独立只读查询可并行；工具失败、无库存或价格变化显示可理解失败，不伪造订单。
- 工具注册表拒绝未注册工具和所有真实写 Skill。

**退出条件**：可演示“旅行请求 → 澄清 → Fake 查询 → 候选对比”，并证明没有真实外部副作用。

## 9. 步骤 7：US5 SSE 与异步辅助能力闭环

**对应任务**：T061～T069。  
**目标**：将 Agent 状态映射为安全 SSE，支持游标补发、状态回退和非阻塞推荐问题。

1. 先编写 SSE 事件契约、断线补发、重复去重和浏览器重连测试。
2. 实现 Agent 内部事件映射、短期事件缓存、API SSE 网关和 `Last-Event-ID` 补发。
3. 实现前端 EventSource、事件去重、重连、状态查询兜底和阶段/错误/候选渲染。
4. 实现标题和推荐问题的异步任务；超时、失败或用户新输入不得改变主 run 结果。

**测试与验收**：

- 每条事件含递增 `event_id`、`run_id`、时间、类型、脱敏 `data` 和 `trace_id`。
- 断开连接不取消后台 run；缓存可补发时按序补发，不能补发时前端以状态查询恢复。
- 重复事件只展示一次；SSE 不输出 Cookie、密钥、提示词、思维链或供应商敏感原文。
- 推荐问题失败可被丢弃，主 run 仍完成。

**退出条件**：可录制并复现一条完整 SSE 时序，包含开始、进度、澄清、工具状态、候选、错误和完成。

## 10. 步骤 8：US6 Fake HITL 与幂等恢复闭环

**对应任务**：T070～T078。  
**目标**：验证高风险动作的确认、审批、拒绝、编辑、超时和恢复，但 Fake 写工具是唯一允许的写工具。

1. 先编写 Fake 写工具、审批权限、浏览器审批、重启幂等的自动化测试。
2. 定义审批动作摘要、决策、版本、超时、角色和幂等键；实现 Fake 写工具并显式拒绝任何真实网络写入。
3. 在 LangGraph 中实现 interrupt、resume 和已完成动作跳过；API 与前端实现审批提交和状态展示。

**测试与验收**：

- 未确认或无权审批时，Fake 写调用次数必须为零。
- 覆盖批准、拒绝、编辑、超时、工具失败、动作版本变化和权限撤销。
- 重启或重复 resume 后，同一幂等键的 Fake 写工具至多执行一次。
- 所有用户可见卡片明确标注为 Fake 演练，不产生订单号、支付或任何真实供应商副作用。

**退出条件**：可演示完整 HITL 状态转移并用调用记录证明“至多一次”。

## 11. 步骤 9：US7 排障、审计与日志闭环

**对应任务**：T079～T085。  
**目标**：让管理员用关联标识定位成功、失败和恢复链路，同时保证日志脱敏与访问审计。

1. 先编写管理员查询、普通用户拒绝、登录/退出审计和敏感字段扫描测试。
2. 实现运行日志/业务审计的逻辑分离、内存测试索引、关联查询 API、管理员页面和关联字段缺失告警。
3. 对 REST、SSE、API↔Agent、模型、记忆/RAG、Skill、Fake 写工具和关键数据库边界统一采用结构化日志字段。

**测试与验收**：

- 以成功、Skill 失败、SSE 断线恢复、会话过期和 Fake 审批各生成一条测试链路。
- 管理员可按 `trace_id`、`request_id`、`run_id` 或 `thread_id` 查询脱敏时序；普通用户不可探测其他用户日志。
- 自动扫描日志，验证码、Cookie、Token、密钥、提示词、思维链和未经脱敏个人文本的出现次数必须为零。
- 脱敏、采集或关联字段失败必须产生告警或明确失败，不能静默丢失。

**退出条件**：任意验收请求均可定位完整脱敏调用链，并可证明日志与业务审计事实分离。

## 12. 步骤 10：P0 集成验收与生产门禁复核

**对应任务**：T086～T094。  
**目标**：将所有用户故事串为 P0 可重复闭环，并将真实生产能力严格留在门禁之后。

1. 建立需求 ID、验收场景、契约、任务和测试的追溯矩阵。
2. 按顺序执行：账号登录 → 会话退出/过期 → 会话/run → 意图 → 澄清/只读查询 → SSE 重连 → Fake HITL → 管理员排障。
3. 记录 L0/L1/L2 基准、L3 阶段事件、日志脱敏扫描和依赖漏洞检查结果。

### G7-2：账号、会话/Run 与审计读写闭环

API Server 已实现可切换的 PostgreSQL 用户目录、脱敏审计服务及会话/Run 服务。启用 `TRAVEL_AGENT_PERSISTENCE_ENABLED=true` 后：登录从 `users` 读取 Argon2id 密码哈希；登录、退出、授权拒绝、管理员查询和 Run 创建写入 `audit_events`；`POST /api/v1/conversations/runs` 原子创建会话、AES-GCM 加密的初始消息，并通过 Docker Secret 保护的内部命令创建 Agent Redis 检查点后将 Run 置为 `running`；`POST /api/v1/runs/{run_id}/resume` 加密保存补充消息后恢复同一线程，`POST /api/v1/runs/{run_id}/cancel` 取消同一 Run；查询接口强制按 `user_id` 隔离。

Redis Run 检查点的开发基线 TTL 为 7 天（`TRAVEL_AGENT_CHECKPOINT_TTL_SECONDS=604800`）。启用顺序：先保持 Compose 中的开关为 `false`，使用 `docker compose -f docker/compose.dev.yml exec -it api-server python scripts/manage_users.py create --username <账号> --role <user|admin>` 创建至少一个账号；再将 Compose 环境变量改为 `true` 并重建 API 与 Agent。账号脚本交互式读取密码，禁止把密码放入命令行或文档。Cookie 会话及登录限流当前仍为 API 进程内状态；跨实例会话持久化需在 Redis 会话策略确认后再实现。

# 企业级智能旅行助手需求文档

> 文档状态：需求与开发治理基线，供产品、业务、前后端和 Agent 团队评审。  
> 目标系统：面向企业用户的长期、可维护旅行管家多智能体系统。  
> 关联文档：[企业级智能旅行助手技术选型](./企业级智能旅行助手技术选型.md)、[企业级智能旅行助手目录结构](./企业级智能旅行助手目录结构.md)、[分阶段实施与测试执行步骤](./企业级智能旅行助手分阶段实施与测试执行步骤.md)、[远程工具沙箱与真实只读接入基线](./远程工具沙箱与真实只读接入基线.md)、[Spec Kit Feature 规格](../specs/001-travel-assistant-mvp/spec.md)。

## 1. 背景与目标

企业员工在差旅前、中、后期需要反复查询航班、火车、酒店、用车、差旅政策和订单状态，并在多个系统之间切换。本系统以长期记忆和多智能体协作为核心，为企业用户提供持续的旅行管家服务：理解用户偏好和企业政策，协助规划行程，查询实时信息，生成预订方案，并在用户明确确认后执行订票或订单变更。

### 1.1 建设目标

- 提供统一的企业差旅对话入口，支持自然语言、多轮对话和结构化表单补充。
- 通过 L1/L2/L3 三层意图识别，降低简单请求延迟与模型调用成本。
- 由 Master Agent 将请求路由到行程规划、预订、信息查询、审核等专用子智能体。
- 所有关键中间状态通过 SSE 向用户同步，用户能够知道系统正在识别、询问、检索、比较还是等待审批。
- 所有外部副作用操作必须获得明确确认，并支持中断、恢复、重试和审计。
- 使用百炼记忆库保存长期偏好，使用百炼托管知识库承载企业政策和知识检索；PostgreSQL 保存业务事实。
- 通过前端、API 后端、Agent 服务分离，保证长期维护和独立扩展能力。

### 1.2 非目标

- 首期不建设复杂 OAuth2、SSO、RBAC 或组织权限中心；仅提供企业内部预置账号密码登录和 API 会话识别，后续预留替换接口。
- 首期不让大模型直接执行任意 Python 代码，不允许绕过工具白名单和审批策略。
- 首期不把百炼记忆库当作订单、支付、审批的主数据源。
- 首期不在 PostgreSQL 创建 RAG 向量表；RAG 由百炼托管知识库提供。
- P0 不执行真实订票、支付、改签、取消、退款或报销提交；仅用 Fake 写工具验证审批、幂等和恢复边界。

## 2. 用户与角色

| 角色 | 主要职责 | 典型权限 |
| --- | --- | --- |
| 用户 | 发起查询、规划、预订和订单服务请求；确认本人行程和低风险执行动作。 | 查看和管理自己的会话、行程、订单；提交澄清、方案选择和本人确认。 |
| 管理员 | 管理企业差旅配置和平台运行；处理需要人工复核的高风险或政策例外操作。 | 管理用户、企业政策、供应商、知识库、工具开关、意图样本和白名单；查看脱敏审计、运行状态；批准、拒绝或编辑需管理员处理的动作。 |

系统中的 Agent 服务、API 后端和运维能力属于系统组件或管理员职责，不作为可登录的第三类用户角色。

## 3. 总体用户旅程

```text
账号密码登录
   ↓
新会话：创建会话并接收首条消息；已有会话：加载会话与相关长期记忆
   ↓
L0 单/多意图判别
   ├─ 明确多意图或不确定 → L3 百炼 LLM 识别
   └─ 单意图 → L1 正则拆分与精确匹配 → L2 RAG 相似匹配 → 问题改写（最多一次）→ L3 兜底
   ↓
意图识别结果 msg 注入 Master Agent
   ↓
用户补充/修正 ─────────────┐
   ↓                       │
Master Agent 路由          │
   ↓                       │
查询/规划子 Agent           │
   ↓                       │
展示候选方案与差异          │
   ↓                       │
用户确认方案 ──────────────┘
   ↓
行程管理工具 + HITL 审批（如需要）
   ↓
执行结果、订单号、行程更新、审计记录
```

核心原则：**Agent 不应在信息不足或用户未确认时直接给出最终方案，更不能直接下单。** Agent 可以给出“当前理解”和“待确认问题”，但最终的推荐方案必须建立在用户确认关键约束后；涉及支付、占座、下单、退改签的动作必须再次确认。

## 4. 功能需求

### 4.1 账号登录与会话

#### 4.1.1 账号预置

- 用户和管理员账号由企业管理员或受控数据库初始化流程预先分配；P0 不提供注册接口。
- 账号密码只以强单向哈希保存，禁止保存或展示明文密码；P0 内存实现已采用 Argon2id。生产哈希参数、账号表字段和独立初始化脚本在 G2/G7 数据库 Schema 评审时确认。
- P0 不提供注册、短信验证码、隐私同意、账号删除、账号禁用、自助改密、找回密码或强制修改初始密码；账号生命周期由企业内部流程管理。
- 普通用户不能自行创建账号、修改角色或提权；系统不设置企业租户绑定。

#### 4.1.2 登录

- 支持账号 + 密码登录；登录成功建立服务端会话，并使用 `HttpOnly`、生产环境 `Secure`、适当 `SameSite` 的 Cookie 保存，前端不得读取或持久化会话令牌。
- API 请求携带服务端可验证的用户上下文；前端不直接提交可任意伪造的 `user_id` 作为唯一安全凭证。
- 支持退出登录、会话过期、主动撤销和基础登录失败提示。当前 P0 开发基线为会话 8 小时；同一账号与来源 IP 在 15 分钟内最多连续失败 5 次，触发后仍返回统一凭据错误。
- 使用 Cookie 的状态变更请求必须具备与部署拓扑匹配的 CSRF 防护。
- 预留未来接入企业 SSO/OIDC 的 `AuthProvider` 抽象，但首期不实现复杂认证中心。

#### 4.1.3 会话管理

- 用户可创建、重命名、归档和删除会话。
- 新会话的首条消息会创建 `conversation_id` 和首个 `run_id`，随后立即进入意图识别；用户不需要先单独创建空会话。
- 已有会话继续运行前，系统加载该会话的可用消息摘要，并检索与当前用户和会话相关的百炼长期记忆后注入上下文；注入内容必须受权限和 token 预算限制。
- 每个会话包含 `conversation_id`；每次运行包含 `run_id`；LangGraph 使用稳定 `thread_id` 进行续跑。
- 会话列表只返回当前用户有权访问的会话；管理员访问平台管理资源时必须记录审计。

### 4.2 前端交互层

技术基线为 React 19 + Vite + TypeScript + Ant Design 6 + Zustand；服务端数据缓存可增加 TanStack Query。

- 登录页：账号、密码输入、错误提示、加载状态、退出登录。
- 助手工作台：会话列表、消息流、输入框、附件/结构化条件入口、运行状态。
- SSE 消息渲染：支持 token、阶段状态、工具摘要、候选方案、澄清问题、审批请求、错误和完成事件。
- 实时思考同步：展示“正在识别意图”“正在确认出行条件”“正在查询航班”“正在比较方案”等**阶段性进度**，不展示模型私有链式思考或敏感内部推理文本。
- 方案卡片：展示候选航班/酒店/行程的价格、时间、规则、来源、限制和推荐理由；字段缺失时明确标记未知。
- 交互确认：用户可以确认条件、修改条件、选择方案、取消运行或要求重新规划。
- HITL 审批卡片：展示待执行动作、参数摘要、风险/政策提示，支持批准、拒绝、编辑和补充说明。
- 断线恢复：SSE 断开后使用 `Last-Event-ID` 重连；重连失败时通过 REST 轮询 run 状态和最终结果。
- 推荐问题：接收异步生成的建议问题，不阻塞主回答；推荐问题必须与当前会话上下文相关且可点击复用。

### 4.3 API/Web 层

API 后端由 FastAPI 实现，职责是协议适配，不承载复杂 Agent 推理。

#### 4.3.1 REST 接口

| 接口 | 说明 |
| --- | --- |
| `POST /api/v1/auth/login` | 登录并建立会话。 |
| `POST /api/v1/auth/logout` | 注销当前会话。 |
| `GET /api/v1/conversations` | 查询会话列表。 |
| `POST /api/v1/conversations` | 创建会话。 |
| `POST /api/v1/conversations/{id}/runs` | 提交用户消息，创建 Agent run。 |
| `GET /api/v1/runs/{id}` | 查询 run 状态和最终摘要。 |
| `POST /api/v1/runs/{id}/resume` | 提交澄清答案、审批决策或编辑后的参数。 |
| `POST /api/v1/runs/{id}/cancel` | 取消尚未完成的运行。 |
| `GET /api/v1/trips` | 查询当前用户可见的行程。 |
| `GET /api/v1/orders` | 查询当前用户可见的订单。 |

#### 4.3.2 SSE 接口

`GET /api/v1/runs/{run_id}/events` 返回 `text/event-stream`，事件必须包含：

| 事件类型 | 用途 |
| --- | --- |
| `run_started` | run 已创建并开始执行。 |
| `intent_recognized` | 返回意图层级、来源、置信度和缺失条件摘要。 |
| `progress` | 当前 Agent 阶段和可展示进度。 |
| `clarification_required` | 请求用户补充或确认信息。 |
| `token` | 面向用户的增量文本。 |
| `tool_status` | 工具调用开始、成功、失败的脱敏状态。 |
| `plan_proposed` | 候选方案或行程草案，等待用户确认。 |
| `approval_required` | 需要用户确认或管理员授权的执行动作。 |
| `recommendations` | 异步推荐问题或相关操作。 |
| `error` | 可恢复或不可恢复错误。 |
| `run_completed` | 运行完成及结果引用。 |

禁止通过 SSE 输出完整系统提示词、模型私有思维链、API Key、证件号、支付信息和第三方敏感原始报文。

### 4.4 Agent 编排层

Agent 服务使用 LangGraph StateGraph 组织长流程。顶层状态建议包含：

```text
TravelAgentState
├── request_context       # user/role/request/conversation/thread/run
├── messages              # 已确认的用户与助手消息
├── context_summary       # 会话压缩摘要及其版本
├── memory_context        # 百炼长期记忆的受控检索结果
├── intent_result         # IntentRecognitionResult
├── intent_result_msg     # 注入 Master Agent 的自然语言识别结论
├── rewrite_trace         # 原始问题、改写问题、次数与原因
├── slots                 # 出发地、目的地、时间、乘客、预算等
├── missing_slots         # 待补充字段
├── user_confirmations    # 用户确认过的条件和方案
├── candidate_plans       # 查询/规划得到的候选方案
├── pending_action        # 待审批或待确认动作
├── tool_history          # 脱敏工具调用摘要
├── errors                # 错误与重试信息
└── status                 # running/clarifying/proposed/awaiting_approval/completed...
```

编排流程：

1. 新会话创建会话和首个 run；已有会话加载会话摘要，并检索相关百炼长期记忆后注入受控上下文。
2. 执行 L0：根据句子长度、强连词和句法分段判断单意图、多意图或不确定。明确多意图或不确定时直接进入 L3；只有明确单意图才进入 L1。
3. 执行 L1：先按正则拆分句子，再对拆分结果进行精确规则匹配。仅一个最终命中时完成识别；两个及以上命中时进入 L3；完全无命中时进入 L2。
4. 执行 L2：对受控意图样本进行 RAG 相似度匹配。Top-1 未达到 0.75 时视为未命中并进入问题改写；Top-1 达到 0.75 后，若 Top-1/Top-2 为同一意图则直接命中；若为不同意图且分差大于 0.05 则命中 Top-1；若分差不大于 0.05 则判为模糊意图，直接交由 L3/Master 澄清，不进行问题改写。
5. L1/L2 均未命中时，调用问题改写 Agent。改写结果保留原文、原因和版本后，重新从 L0 进入上述流程；改写最多一次，第二轮仍未由 L1/L2 命中时直接进入 L3，禁止循环改写。
6. L3 使用百炼 LLM 完成多意图或兜底意图识别，并输出受服务端校验的 `IntentRecognitionResult`。
7. 将最终意图识别结论转换为自然语言 `intent_result_msg` 注入 Master Agent；同时保留结构化状态供路由、审计和白名单校验使用。
8. Master Agent 根据意图、白名单、会话状态和用户确认信息分配业务子 Agent。
9. 子 Agent 按需并行调用彼此独立的只读 Skill，形成候选信息或行程草案；向用户展示阶段状态、已知条件和待确认项。
10. 用户确认方案后，ItineraryManageAgent 对有副作用操作执行 Middleware 审批或流程级 `interrupt()`；用户确认或管理员授权恢复后才可执行。
11. 执行结果写入 PostgreSQL 的订单/行程事实；对话稳定后异步写入百炼记忆库，并异步生成标题和推荐问题。

### 4.5 16 类意图识别

系统将定义 16 类意图，由 Master Agent 按意图白名单分配至多个业务子 Agent。当前阶段暂不填写意图名称、编码、槽位或 Agent 分配，避免在业务范围未评审完成前冻结路由规则。

正式落地前必须确认：16 类意图的名称与 `intent_code`、各意图必填槽位、归属子 Agent、L0 强连词/不确定性规则、L1 规则样本、L2 RAG 样本、L2 相似度阈值与 Top-1/Top-2 相似度分差阈值、L3 输出约束、白名单版本。

#### 4.5.1 三层意图识别与问题改写的边界

- L0 不能仅凭“句子较长”判定多意图；长度和强连词只作为启发式信号，无法确定时必须保守地交给 L3，避免把多项出行需求错误拆开。
- L1 的“完全命中”以意图规则的唯一最终命中为准，而不是任意关键词出现；拆分后的多个有效匹配视为多意图，进入 L3 统一识别。
- 状态陈述混合多个连续动作（例如“审批通过了，帮我规划行程订酒店”）不得仅因其中包含“规划行程”而被 L1 短路为单意图；L1 视为非最终未命中，L2 单条近邻无法确认复合诉求时返回 empty，执行一次问题改写后由 L3 输出多意图。
- L2 的 Top-1/Top-2 比较必须以同一版本的意图样本库和可解释的相似度分数为依据。Top-1 达到 0.75 后，同意图直接命中；不同意图按 0.05 分差区分“命中 Top-1”和“模糊澄清”。
- 问题改写只用于 L1/L2 未命中造成的表达歧义，不得改变订单号、航班号、日期、金额、地点和用户明确约束。原始问题和改写问题必须同时保留并可追溯。
- L3 不因改写失败而反复调用改写 Agent；一次改写后的 L1/L2 仍未命中即进入 L3。

### 4.6 业务子智能体

| 子智能体 | 责任 | Skill 与交互边界 |
| --- | --- | --- |
| `ItineraryPlanAgent` | 收集条件、规划出行和生成候选行程草案。 | 可按需并行调用地图、天气、航班、火车、酒店、用车等只读 Skill；信息不足时只澄清，不输出未经确认的最终方案。 |
| `ItineraryManageAgent` | 查询可订资源、管理预订、改签、取消和已确认行程。 | 通过受控 Skill 调用实时查询或写操作；写操作必须先展示执行计划，再完成用户确认/HITL。 |
| `ItineraryReviewAgent` | 对候选方案和待执行动作进行政策、预算、规则和风险审核。 | 输出审核结论与理由；不能代替用户或管理员做最终授权。 |
| `InfoAgent` | 查询订单、行程、航班、火车、酒店、用车、目的地与政策信息。 | 实时结构化信息通过 Skill 查询；政策和知识问答调用百炼知识检索。 |
| `ReimbursementAgent` | 协助理解差旅报销规则、材料、金额和报销进度。 | 首期以只读政策/报销信息查询为主；实际提交报销申请是否纳入范围待确认。 |

#### 4.6.1 模型、迭代与并行策略

- 五个业务子智能体可配置不同的百炼模型、系统提示词、上下文预算和 `maxIters`；模型名称和每个 Agent 的具体 `maxIters` 当前暂不填写，必须在成本、质量和延迟评测后锁定。
- `maxIters` 是单次 Agent 运行中“模型决策 → 工具调用 → 观察结果”循环的上限；到达上限时 Agent 必须输出可解释的中止/澄清状态，不能静默继续循环。
- 工具调用按需并行：仅当工具相互独立、只读且无共享副作用时才能并行，例如并行查询航班与酒店；占座、下单、改签、取消、退款和任何依赖前一步结果的工具必须串行。
- 仅对可判定的瞬时网络错误执行指数退避重试；业务错误、参数错误、政策拒绝、无库存、价格变化和非幂等写操作不得自动重试。即使网络重试，写操作也必须携带幂等键。

#### 4.6.2 Master Agent 与子智能体的通信

- Master Agent 向子智能体传递的任务正文采用自然语言任务简报，而非把完整业务语义拼装为 JSON。简报应说明用户目标、已确认条件、未确认条件、限制、可用 Skill 与期望输出。
- `intent_result_msg` 是 Master Agent 的输入之一，必须清楚说明识别来源、单/多意图结论、置信度、改写痕迹和待澄清项。
- 自然语言简报不承担安全边界：`user_id`、`thread_id`、角色、工具白名单、审批状态、幂等键和 Skill 参数校验仍由 LangGraph 状态和服务端代码以结构化方式保留与校验。
- 子智能体返回给 Master Agent 的解释性内容可为自然语言；运行状态、工具审计和写操作结果必须保留可验证的结构化记录。

### 4.7 辅助子智能体

#### 标题生成 Agent

- 在会话首轮或主题明显变化时异步生成简短标题。
- 只使用已确认的用户输入和会话摘要，不读取证件、支付等敏感字段。
- 生成失败不影响主流程，使用默认标题兜底。

#### 推荐问题 Agent

- 在主流程达到稳定节点后异步生成 3~5 个下一步问题或操作建议。
- 推荐问题必须与当前意图、缺失槽位、候选方案相关，不能诱导未经授权的高风险操作。
- 生成失败、超时或用户开始新输入时可丢弃，不阻塞主 SSE。

#### 记忆整理任务

- 对话完成或达到稳定节点后异步调用百炼记忆库，提取用户偏好、常用出发地、座位/房型偏好等长期信息。
- 不将订单状态、支付结果和审批决定仅写入记忆库；这些数据以 PostgreSQL 为准。

### 4.8 上下文压缩与长期记忆注入

- 当当前会话的上下文 token 使用量达到该 Agent 已配置上下文预算的 75%，或累计消息数超过 60 条时，必须在下一次模型调用前执行上下文压缩。
- 压缩结果必须保留：当前用户目标、已确认/未确认槽位、最终意图结果、原始/改写问题、候选方案、待审批动作、工具执行结果摘要、错误状态和最近若干轮原始消息。
- 压缩后的摘要以版本化 `context_summary` 保存；同一段历史不得反复摘要造成关键信息漂移。用户可通过后续消息纠正摘要中的错误。
- 已有会话恢复时，先加载压缩摘要，再从百炼记忆库检索与该用户、会话和当前请求相关的少量长期记忆。记忆检索结果是补充上下文，不覆盖已确认的会话事实。
- 上下文预算暂不固定。不同 Agent 使用不同模型时，必须在模型选型评测中分别确定其上下文预算，确保可覆盖系统提示词、工具定义、长期记忆、任务简报和模型输出。

## 5. 交互与确认规则

### 5.1 不直接给出方案

Agent 每次响应应优先遵循以下结构：

```text
当前理解：……
已确认条件：……
还缺少的信息：……
下一步我可以：……
请确认/补充：……
```

只有满足以下条件，才允许展示候选方案：

- 关键槽位达到该意图定义的完整度；
- 已识别用户和企业政策上下文；
- 查询结果来自可追溯的工具或百炼知识检索；
- 明确标注价格、库存、时刻等动态信息的查询时间；
- 对存在多个合理选择的情况，至少展示选择差异，而不是替用户默认选择。

### 5.2 思考过程同步

系统只同步可解释的阶段状态和行动摘要，不输出模型隐私思维链。推荐状态：

`接收请求` → `识别意图` → `确认出行条件` → `查询资源` → `比较方案` → `等待选择` → `政策审核` → `等待审批` → `执行预订` → `更新行程` → `完成`。

每个状态应包含 `stage_code`、面向用户的 `message`、开始时间、可选进度百分比和关联工具摘要。发生错误时说明“下一步可重试/修改/取消”，不暴露堆栈、供应商密钥或内部提示词。

### 5.3 多轮澄清

- 一次最多询问 1~3 个高价值问题，按对后续决策的影响排序。
- 用户回答后只更新相关槽位，不覆盖已确认且未被用户修改的条件。
- 用户说“随便”“你决定”时，Agent 仍需声明默认假设并请求确认，不能将模糊授权当作下单授权。
- 用户可以随时纠正意图，例如“我不是要订票，只想查政策”；系统应保留修正来源并重新路由。

## 6. 数据与状态需求

### 6.1 PostgreSQL 业务实体（逻辑需求）

首期建议包含以下逻辑实体，具体字段和 schema 需在实现前评审：

- `User`：用户基本资料、角色、登录状态摘要。
- `Conversation`：会话标题、用户、状态、创建/更新时间。
- `Message`：用户消息、助手可见消息、事件引用和脱敏内容。
- `Run`：运行 ID、thread ID、意图结果摘要、当前状态、错误、开始/结束时间。
- `Trip`：行程日期、地点、参与人、确认状态和订单关联。
- `Order`：供应商、订单类型、外部订单号、金额摘要、状态和幂等键。
- `Approval`：审批动作、处理角色（用户或管理员）、处理人、决定、版本、时间和理由。
- `AuditEvent`：关键路由、工具调用、审批和状态变化的脱敏审计记录。

### 6.2 Redis 数据

- LangGraph durable checkpoint：按 `thread_id` 保存可恢复图状态。
- SSE 事件短缓存：按 `run_id + event_id` 保存断线补发窗口。
- 限流和幂等辅助键：保护登录、run 创建、resume 和外部写操作。
- 不将 Redis 作为订单主数据、永久审计或唯一恢复来源。

### 6.3 百炼记忆与 RAG

- 记忆库 Scope 至少区分应用、用户、Agent 和运行上下文。
- RAG 知识库按企业政策、供应商规则、目的地知识等主题划分，并维护知识库 ID 与权限映射。
- 记忆库和 RAG 返回结果必须携带来源/版本或可追溯标识，便于问题定位和审计。

### 6.4 全链路日志与问题定位

- 每一次外部 REST 调用、SSE 建连/重连/关闭、API 与 Agent 的内部命令、LangGraph 节点执行、百炼调用、记忆/RAG 检索、Skill 调用和关键数据库访问，均须产生结构化运行日志；日志至少携带 `trace_id`、`request_id`、`run_id`、`thread_id`、`conversation_id`、用户脱敏标识、接口/节点名称、调用方向、耗时、结果状态、错误码和重试信息。
- 对请求与响应只记录经字段级脱敏和大小限制后的可诊断摘要：允许记录协议版本、参数名称、业务字段白名单、内容哈希、长度、供应商请求 ID、结果摘要与错误摘要；禁止默认保存完整原始报文。
- 绝不记录登录密码、Cookie、Authorization / API Key、支付/证件信息、完整系统提示词、模型私有思维链和未经脱敏的个人行程文本。若未来确需保留原文排障，必须先单独确认加密存储位置、最小访问角色、审计、保留期限与删除机制。
- `AuditEvent` 用于不可抵赖的业务审计，运行日志用于排障与性能分析；二者通过关联标识互相跳转，但运行日志不能替代审批、订单和状态变更的业务事实。
- 管理员仅能在授权范围内按关联标识检索脱敏链路；普通用户不可查询其他用户的运行日志。日志采集、脱敏失败或关联字段缺失必须触发告警，不能静默丢失。

## 7. 异常、降级与安全需求

- 百炼超时：保留当前 run 状态，向用户发送可重试事件，不重复执行已完成的工具。
- 供应商无库存或价格变化：标记候选失效，要求用户重新选择，不静默替换。
- SSE 断开：Agent run 继续；客户端使用 `Last-Event-ID` 或 REST 查询恢复界面。
- Agent 服务不可用：API 返回可识别的运行状态和稍后重试建议，不伪造成功结果。
- 工具失败：记录结构化错误和重试次数；仅对瞬时网络故障执行退避重试，业务错误和非幂等写操作不得自动重试，所有写操作必须使用幂等键。
- 所有用户、会话和订单访问进行服务端校验；日志脱敏手机号、证件、支付信息、API Key 和完整模型输入。
- Cookie 必须使用 `HttpOnly`、生产环境 `Secure` 和适当 `SameSite` 属性；所有 Cookie 状态变更请求均须校验 CSRF。用户退出后当前会话失效；会话过期后必须拒绝访问受保护资源。
- Agent 输出不可信：所有结构化输出、工具参数、供应商响应均经过 Pydantic/白名单/业务规则校验。

## 8. 非功能需求与验收指标

指标数值需结合企业并发规模确认，以下作为首轮验收维度：

| 维度 | 验收要求 |

## 10. P0 实施需求与开发指南

> 版本：v0.1（待评审）  
> 本章将前述需求转化为可按顺序开发、联调和验收的 P0 基线；技术依据参见[技术选型](./企业级智能旅行助手技术选型.md)和[目录结构](./企业级智能旅行助手目录结构.md)。

### 10.1 P0 目标、边界与开工门禁

#### 10.1.1 一句话目标

一名已登录用户能够创建或继续一个旅行会话，经 L0/L1/L2/L3 意图识别和必要的澄清后，获得可解释的旅行信息或行程草案；系统通过 SSE 展示阶段状态，并在有副作用的行程管理动作前等待用户确认或管理员授权。

#### 10.1.2 已锁定范围

| 项目 | P0 范围 | 验证目的 |
| --- | --- | --- |
| 前端 | React 19 + Vite + Ant Design 6 + Zustand，桌面端优先 | 验证对话、SSE、方案卡片和审批卡片闭环。 |
| 身份 | 企业预置账号 + 密码；角色只有用户、管理员 | 不提供注册和短信流程，保留最小权限边界。 |
| 服务分离 | Web、API 后端、Agent 服务独立目录和部署单元 | 验证前端/API/Agent 的可维护边界。 |
| Agent | LangGraph；L0/L1/L2/L3、一次问题改写、Master Agent、五个业务子 Agent | 验证多智能体路由与可恢复对话。 |
| 交互 | REST 创建/恢复 run，SSE 推送事件，POST 提交澄清/确认/审批 | 验证长流程不因连接断开而丢失。 |
| 业务能力 | 行程规划、信息查询、行程管理、审核、报销信息查询 | 验证核心旅行管家流程；具体 16 类意图暂不冻结。 |
| 外部能力 | 航班、火车、酒店、用车等通过受控 Skill；政策/RAG 使用百炼知识检索 | 隔离供应商变化和工具权限。 |
| 数据 | PostgreSQL 记录业务事实和审计索引；Redis 保存 checkpoint 与事件短缓存；百炼记忆库存长期记忆 | 验证可恢复和可审计边界。 |

#### 10.1.3 明确不做

- 不提供注册、短信验证码、复杂 SSO、OAuth2、MFA、移动端 Token、组织权限中心、隐私同意、账号删除、账号禁用、自助改密、找回密码、强制修改初始密码或第三种登录角色。
- 不让模型直接访问数据库、执行任意 Python 代码，或绕过 Skill 白名单调用供应商。
- 不在未确认供应商、审批和幂等策略前接入真实扣费、占座、下单、退改签或报销提交。
- 不创建 pgvector 内容表或自建 RAG 向量库；RAG 继续由百炼托管知识库承载。
- 不展示模型私有思维链、系统提示词、密钥、证件、支付信息或供应商原始敏感报文。
- 不在 P0 冻结 16 类意图具体名称、模型名称、上下文预算或各 Agent 的 `maxIters`。

| --- | --- | --- |
| P0-CONV-001 | 新会话首条消息自动创建会话与 run。 | 单次请求创建一个 `conversation_id` 和一个 `run_id`，随后进入意图流程。 |
| P0-CONV-002 | 已有会话可继续运行。 | 使用同一 `thread_id` 续跑；读取会话摘要和受控长期记忆。 |
| P0-SSE-001 | 前端能订阅 run 的 SSE 事件。 | 顺序接收 `run_started`、`progress`、`clarification_required`、`plan_proposed`、`approval_required`、`run_completed` 等事件。 |
| P0-SSE-002 | SSE 断线可恢复。 | 客户端带 `Last-Event-ID` 重连可补发短期事件；无法补发时可由 `GET /runs/{id}` 恢复状态。 |
| P0-RUN-001 | run 可取消或恢复。 | 未完成 run 可取消；澄清/审批后使用同一 run 或受控续跑命令恢复，不能重复执行写操作。 |

#### 10.2.3 意图识别与问题改写

| 需求 ID | 需求 | 验收标准 |
| --- | --- | --- |
| P0-INTENT-001 | L0 判断单意图、多意图或不确定。 | 明确多意图和不确定输入进入 L3；不能仅由句长断言多意图。 |
| P0-INTENT-002 | L1 对单意图输入按正则拆分后精确匹配。 | 唯一最终命中结束 L1；两个及以上命中进入 L3；无命中进入 L2。 |
| P0-INTENT-003 | L2 进行意图样本 RAG 相似匹配。 | 只有 Top-1 达阈值、Top-1/Top-2 同意图且相似度分差不超过配置阈值时命中；输出样本库版本和分数摘要。 |
| P0-REWRITE-001 | L1/L2 未命中后只改写一次。 | 保留原始问题、改写问题、原因和版本；改写后重走 L0；第二轮未命中直接 L3。 |
| P0-INTENT-004 | L3 生成可校验的最终识别结果。 | 输出受服务端校验的 `IntentRecognitionResult`；白名单外的 Agent 不可被路由。 |
| P0-INTENT-005 | 识别结果对 Master Agent 可解释。 | 生成自然语言 `intent_result_msg`，包含来源、单/多意图、置信度、改写痕迹和待澄清项。 |

#### 10.2.4 Master Agent、子 Agent 与工具

| 需求 ID | 需求 | 验收标准 |
| --- | --- | --- |
| P0-MASTER-001 | Master Agent 按意图和状态路由。 | 仅向白名单子 Agent 分配任务；路由、改写和失败回退均写入脱敏审计事件。 |
| P0-AGENT-001 | 支持五个业务子 Agent。 | 可分别调用 `ItineraryPlanAgent`、`ItineraryManageAgent`、`ItineraryReviewAgent`、`InfoAgent`、`ReimbursementAgent`。 |
| P0-AGENT-002 | Master 与子 Agent 使用自然语言任务简报。 | 简报包含目标、已确认/未确认条件、约束、可用 Skill 和期望输出；不以自然语言传递用户身份、权限、幂等键等安全字段。 |
| P0-AGENT-003 | 各 Agent 独立配置模型与迭代上限。 | 配置可按 Agent 生效；达到 `maxIters` 必须返回可解释中止/澄清状态。 |
| P0-SKILL-001 | 实时旅行信息由 Skill 查询。 | 航班、火车、酒店、用车查询只经受控 Skill；模型无法调用未注册 Skill。 |
| P0-SKILL-002 | 工具按安全条件并行。 | 独立只读 Skill 可并行；写操作和依赖操作串行；每次调用有超时、审计和用户上下文。 |
| P0-SKILL-003 | 自动重试只用于网络瞬态故障。 | 指数退避仅作用于可判定网络失败；业务失败、无库存、价格变化、政策拒绝和非幂等写操作不自动重试。 |

#### 10.2.5 行程、审核和人机协作

| 需求 ID | 需求 | 验收标准 |
| --- | --- | --- |
| P0-PLAN-001 | 行程规划先澄清、后生成候选草案。 | 关键槽位缺失时最多提 1~3 个高价值问题；不直接替用户作最终选择。 |
| P0-PLAN-002 | 候选方案具有可解释性。 | 展示价格/时刻/规则/来源/查询时间/待确认项；缺失字段显式标记。 |
| P0-REVIEW-001 | 审核 Agent 输出结构化审核结论。 | 至少区分可执行、需补充信息、政策例外和不可执行，并给出面向用户的理由。 |
| P0-HITL-001 | 写操作执行前必须确认。 | 用户确认或管理员授权前，Skill 不执行占座、下单、改签、取消、退款或报销提交。 |
| P0-HITL-002 | 审批中断可恢复且幂等。 | 通过同一 `thread_id` 恢复；重复恢复不产生重复写操作。 |

#### 10.2.6 长期记忆、压缩与辅助任务

| 需求 ID | 需求 | 验收标准 |
| --- | --- | --- |
| P0-MEM-001 | 已有会话可注入相关长期记忆。 | 记忆按 Scope 和权限过滤，只注入当前请求相关内容，不覆盖已确认会话事实。 |
| P0-MEM-002 | 会话超预算时压缩。 | token 使用达到 Agent 上下文预算的 75% 或消息数超过 60 条时，下一次模型调用前生成版本化摘要。 |
| P0-MEM-003 | 压缩不丢关键状态。 | 摘要保留意图、槽位、改写痕迹、候选方案、待审批动作、工具结果和错误摘要。 |
| P0-AUX-001 | 标题和推荐问题异步生成。 | 主 run 不等待它们完成；失败可丢弃且不影响旅行结果。 |

#### 10.2.7 全链路日志与问题定位

| 需求 ID | 需求 | 验收标准 |
| --- | --- | --- |
| P0-OBS-001 | 所有系统边界均生成结构化运行日志。 | REST、SSE 生命周期、API↔Agent 命令、Agent 节点、百炼/记忆/RAG、Skill 和关键数据库访问均记录 `trace_id`、`request_id`、`run_id`、`thread_id`、调用名称、方向、耗时、结果、错误码与重试次数。 |
| P0-OBS-002 | 单次用户操作可追溯完整脱敏调用链。 | 输入一个 `request_id`、`run_id` 或 `thread_id`，可查询对应 API、Agent、模型与 Skill 的时序、请求/响应摘要及失败位置；关联字段缺失视为测试失败。 |
| P0-OBS-003 | 接口内容按安全规则记录。 | 请求/响应仅记录字段白名单、脱敏摘要、长度、哈希、供应商请求 ID 和错误摘要；验证码、凭据、令牌、支付/证件信息、完整提示词、思维链和未经脱敏的个人文本不得进入运行日志。 |
| P0-OBS-004 | 日志可安全检索并能发现采集故障。 | 仅授权管理员可查询脱敏日志，查询行为可审计；脱敏、采集或关联失败产生可观测告警，不能静默忽略。 |

### 10.3 核心接口与事件契约

#### 10.3.1 外部 REST API

| 方法与路径 | 责任 | P0 返回/约束 |
| --- | --- | --- |
| `POST /api/v1/auth/login` | 预置账号密码登录 | 建立安全 Cookie 会话；不回显密码或会话密钥。 |
| `POST /api/v1/auth/logout` | 退出当前会话 | 使当前会话失效。 |
| `POST /api/v1/conversations/{id}/runs` | 在已有会话提交消息 | 返回 `run_id`、状态和事件地址。 |
| `POST /api/v1/conversations/runs` | 新会话首条消息 | 创建会话和 run。 |
| `GET /api/v1/runs/{id}` | 查询运行状态 | 仅返回当前用户可访问的 run。 |
| `GET /api/v1/runs/{id}/events` | SSE 订阅 | 支持 `Last-Event-ID`。 |
| `POST /api/v1/runs/{id}/resume` | 提交澄清、选择、确认或管理员决策 | 使用稳定 `thread_id` 续跑。 |
| `POST /api/v1/runs/{id}/cancel` | 取消运行 | 不回滚已完成的外部副作用；返回当前事实状态。 |

所有写接口均要求 `request_id`；有外部副作用的接口还要求服务端生成/校验幂等键。具体字段在 `packages/contracts` 中以 OpenAPI/JSON Schema 固化，前端不得复制手写不受版本控制的类型。

#### 10.3.2 SSE 最小事件契约

每个事件至少有 `event_id`、`run_id`、`timestamp`、`type`、`data`。事件 `data` 只可含展示所需脱敏信息。

| 事件 | 最小 data | 用途 |
| --- | --- | --- |
| `run_started` | `conversation_id`、`status` | 显示运行已开始。 |
| `intent_recognized` | `source`、`intent_summary`、`confidence`、`missing_slots` | 显示系统理解，不展示内部推理。 |
| `progress` | `stage_code`、`message` | 显示可解释阶段，如识别、查询、审核。 |
| `clarification_required` | `questions`、`reason` | 用户补充必要条件。 |
| `tool_status` | `skill_name`、`status`、`summary` | 展示脱敏工具进度。 |
| `plan_proposed` | `plan_id`、`options`、`assumptions` | 展示候选方案，等待选择。 |
| `approval_required` | `action_summary`、`allowed_decisions` | 用户确认或管理员授权。 |
| `recommendations` | `items` | 异步建议问题。 |
| `error` | `code`、`message`、`retryable` | 安全的失败说明。 |
| `run_completed` | `status`、`result_ref` | 结束当前 run。 |

#### 10.3.3 Agent 内部命令边界

API 后端向 Agent 服务发送 `start`、`resume`、`cancel` 命令；Agent 服务只返回版本化状态和事件。任务正文可以是自然语言，以下安全元数据必须由服务端提供和校验：`user_id`、`conversation_id`、`thread_id`、`run_id`、角色、Agent/Skill 白名单、审批状态、幂等键和 trace 标识。`suspend_user_memory` 仅作为非 P0 的内部技术预留，没有浏览器或 P0 API 入口。

### 10.4 核心状态机与流程

#### 10.4.1 Run 状态机

```text
created → running → clarifying ───────────────┐
                  │                            │ resume
                  ├→ proposed ─────────────────┤
                  ├→ awaiting_approval ────────┤
                  ├→ failed                    │
                  ├→ cancelled                 │
                  └────────────────────────────┘
                              ↓
                         completed
```

- `clarifying`：等待用户补充字段或纠正意图。
- `proposed`：候选方案已生成，等待用户选择或确认。
- `awaiting_approval`：存在有副作用动作，等待用户确认或管理员授权。
- `failed`：记录失败类别和是否可重新发起；不得伪装成功。
- `cancelled`：停止未开始的后续步骤；已经执行的外部操作以供应商和订单事实为准。

#### 10.4.2 意图识别流程

```text
输入消息
  ↓
L0：明确多意图/不确定 ───────────────────────────→ L3
  ↓ 明确单意图
L1：唯一最终规则命中 ─────────────────────────────→ 识别结果
  ↓ 无命中                    ↓ 两个及以上命中
L2：RAG 相似度判断 ───────────┴──────────────────→ L3
  ↓ 未命中
问题改写（仅一次） → 重走 L0/L1/L2 → 仍未命中 → L3
  ↓
IntentRecognitionResult + intent_result_msg → Master Agent
```

#### 10.4.3 写操作流程

```text
候选方案 → 用户选择 → ItineraryReviewAgent → 执行计划展示
                                               ↓
                       用户确认 / 管理员授权（HITL）
                                               ↓
                              带幂等键的串行 Skill 调用
                                               ↓
                         PostgreSQL 事实写入 + SSE 结果
```

### 10.5 数据、配置和迁移边界

#### 10.5.1 P0 逻辑实体

 P0 已落地 `User`、`Conversation`、`Message`、`Run`、`Trip`、`TravelPolicyRule`、`AuditEvent` 七类 PostgreSQL 表；其职责沿用本文第 6 章。用户账号与档案合并为 `users`，手机号、证件号、姓名拼音等高敏字段只以 AES-256-GCM 密文、nonce 和 key_version 保存，`SensitiveMasker` 仅用于日志/展示脱敏。订单、预订、审批、报销和 RAG 向量表不在本次迁移范围内。

迁移入口为 `migrations/api-server/versions/20260819_0001_p0_core_schema.py`，由 Compose 的 `db-migrate` 一次性执行并通过 `alembic_version` 管理。独立账号脚本为 `scripts/manage_users.py`，只允许交互式输入密码，不接受命令行明文密码。Docker Secret `data_encryption_key` 提供 32 字节 Base64 密钥。

P0 默认保留期限：会话、消息、Run 和行程候选自最后活动起 365 天；脱敏审计 180 天；账号停用/删除后的敏感档案 30 天。当前不启用自动清理作业，生产上线前需补充删除任务、备份/灾备和审计访问复核。

当前 PostgreSQL 读写闭环以功能开关 `TRAVEL_AGENT_PERSISTENCE_ENABLED` 控制：关闭时保留自动化测试所需的内存账号/审计替身；开启时只接受企业管理员通过独立脚本预置的 `users` 账号，创建会话和 Run 时用户消息必须加密落库，审计必须携带 `trace_id`、`request_id`、`run_id`、`thread_id`。会话 Cookie 与登录限流尚未迁入 Redis，不得将当前单实例会话能力描述为跨实例可恢复。

#### 10.5.2 配置必须版本化

以下配置不写死在提示词或代码中，应有版本号、启用状态、审计和回滚能力：

- L0 强连词与不确定规则；L1 正则规则；L2 意图样本和阈值；16 类意图与白名单。
- Agent → 百炼模型、上下文预算、`maxIters`、提示词版本、允许的 Skill。
- Skill 超时、重试、并行性、审批等级、幂等策略。
- 百炼记忆 Scope、知识库 ID、检索权限和脱敏规则。

#### 10.5.3 单一事实源

- PostgreSQL：用户、会话、run 索引、行程、订单、审批和审计事实。
- Redis：LangGraph checkpoint、短期 SSE 事件、限流和幂等辅助键；不作永久业务事实。
- 百炼记忆库：长期偏好和可检索记忆；不保存唯一订单事实。
- 百炼知识检索：政策和知识片段；应用保存关联 ID、版本和权限映射。

### 10.6 推荐实施顺序

#### 步骤 0：完成门禁评审

确认 G1~G9 或明确每项的 Fake Adapter 策略。G7 已局部解锁，可进入本文限定的 P0 PostgreSQL 迁移；没有 G1/G2/G4/G8/G9，不进入对应的真实供应商、生产认证、生产审批、生产日志或容量发布实现。

#### 步骤 1：建立仓库骨架、契约和健康检查

创建 `apps/web`、`services/api-server`、`services/agent-server`、`packages/contracts` 的空壳；先定义 OpenAPI、Agent 命令和 SSE 事件 Schema，再建立三个服务的健康检查与本地联通。

#### 步骤 2：完成最小认证和会话访问控制

实现预置账号测试夹具、用户/管理员会话、私有资源校验和认证限流。生产账号预置责任、密码哈希参数和管理员角色授予方式在 G2 前不得自行假设。

#### 步骤 3：实现会话、run 与 SSE 空闭环

前端可创建会话、提交消息、订阅 SSE、断线重连、查看 run 状态和取消运行。此阶段 Agent 服务可返回确定性模拟事件，用以确认协议与 UI。

#### 步骤 4：实现可测试的 L0/L1/L2/L3 管线

先实现 L0/L1 的纯规则测试，再在 G1 确认后接入 L2 样本 RAG 和 L3 百炼 Adapter；覆盖多意图、未命中、改写一次、二次未命中和白名单拒绝。

#### 步骤 5：实现 Master 与单个只读 Agent 闭环

先选择一个已确认的只读 Skill，用 `InfoAgent` 或 `ItineraryPlanAgent` 完成“识别 → 澄清 → 查询 → SSE 结果”的最小闭环；其他 Agent 只保留受契约覆盖的占位实现。

#### 步骤 6：接入长期记忆、摘要和辅助任务

在会话恢复时检索受控长期记忆；实现 75% token 或 60 条消息的压缩触发；标题和推荐问题以不阻塞主 run 的异步方式运行。

#### 步骤 7：实现审核、HITL 与行程管理写流程

在 G3/G4 确认后接入 `ItineraryReviewAgent`、`ItineraryManageAgent` 和写 Skill。先验证用户确认、管理员授权、中断恢复、重复恢复和供应商失败，不接入真实扣费前不得发布写按钮。

#### 步骤 8：完善可观测性、测试与发布策略

先落实统一关联标识、日志字段契约与脱敏器，再贯通 `trace_id`、`request_id`、`run_id`、`thread_id` 的结构化日志和追踪。日志需覆盖 REST、SSE、API↔Agent、Agent 节点、百炼/记忆/RAG、Skill 和关键数据库边界；补齐单元、契约、集成和端到端测试；在预发布环境演练断线、重试、恢复、库存变化、权限隔离和日志检索。

### 10.7 P0 发布阻断验收

- 用户不能读取、恢复或订阅其他用户的会话与 run。
- SSE 不输出思维链、密钥、证件、支付数据或供应商敏感报文。
- L0/L1/L2/L3、改写次数、路由和 Agent/Skill 白名单均能从审计事件追溯。
- 任意写 Skill 在用户确认/管理员授权前都不会执行；重试和恢复不会造成重复写入。
- 网络故障、SSE 断开、Agent 重启后，run 能显示真实状态；中断流程可用相同 `thread_id` 恢复。
- 上下文压缩不会丢失已确认条件、待审批动作和工具结果；长期记忆不覆盖订单/审批事实。
- 所有外部依赖均有超时、脱敏日志和可控失败文案；未配置的真实 Skill 以禁用或 Fake Adapter 运行，不伪造外部成功结果。
- 任意一条测试请求均可按关联标识定位其 API、Agent、模型与 Skill 调用链；日志不含验证码、凭据、令牌、支付/证件信息、完整提示词、思维链或未经脱敏的个人文本。

### 10.8 P0 Definition of Done

P0 达到完成条件，必须同时满足：

1. 步骤 1~6 的最小只读旅行管家闭环在本地与测试环境可重复演示。
2. 每个已开启的外部 Skill、百炼 Adapter、认证 Adapter 都有失败路径和契约测试。
3. G1~G9 中未确认的能力没有被伪装为已上线功能，并在 UI/API 中显示明确的不可用或待配置状态。
4. 所有需求 ID 至少关联一个自动化测试、契约测试、端到端测试或书面人工验收用例。
5. 安全、用户资源隔离、HITL、幂等、SSE 断线恢复、审计和全链路日志项目通过发布阻断验收。
6. Cookie/CSRF、账号密码登录、会话退出和过期、角色隔离均通过自动化或书面验收；未确认的账号数据保留与备份策略不得被实现默认锁定。

### 10.9 开工前剩余的关键决策

当前最优先的不是扩充 Agent 数量，而是确认以下顺序：

1. 16 类意图与其 L0/L1/L2/L3 样本/阈值（G1）；
2. 账号预置责任、密码哈希参数与管理员授予方式（G2）；
3. 第一个可真实调用的只读 Skill 及其成本、权限、超时（G3）；
4. 用户确认与管理员授权的写操作矩阵（G4）；
5. PostgreSQL schema 与迁移所有权（G7）；
6. 五个 Agent 的模型、预算与 `maxIters`（G6）；
7. 日志平台、字段脱敏、访问控制、保留期限、告警与原文例外留存策略（G8）。

在这些决策完成前，可以安全推进前端静态 UI、契约、SSE 模拟流、Fake Adapter、规则引擎单元测试和服务健康检查；不得开始真实预订、未获确认的持久化 schema 或生产百炼数据接入。

## 11. Spec Kit 开发治理基线与可追溯性

本章融合 Feature `001-travel-assistant-mvp` 的 Spec Kit 规格、计划、研究、逻辑数据模型、契约、验证指南和任务清单。它不替代 `specs/` 下的版本化细节；后者是本 Feature 实施时的精确任务与契约来源。若本文与对应 Feature 产物冲突，以最新经过澄清的 Feature 规格为准，并同步回本文。

### 11.1 项目宪章

所有开发、评审和发布应遵循以下原则：

1. **需求与边界优先**：先有范围、验收标准和非目标，再进入实现；未确认模型、供应商、Schema、成本、安全或上线策略不得由代码默认决定。
2. **契约优先与服务边界**：Web、API Server、Agent Server 仅通过版本化 REST、SSE 和内部命令契约通信；前端不直连 Agent、数据库、Redis、百炼或供应商。
3. **数据可信可追溯**：旅行动态数据必须关联来源、时间和版本；记忆/RAG 只能补充上下文，不能覆盖已确认业务事实。
4. **性能与成本可度量**：L0/L1 p95 小于 50ms、L2 p95 小于 100ms；L3 等待期间先发送阶段事件。未确认的并发、SSE 规模、L3 上限、可用性和预算只可测量，不可宣称达标。
5. **有状态流程可恢复且安全**：以稳定 `thread_id`、检查点、幂等键、权限校验和 HITL 保证中断可恢复；SSE 断开不等于取消 run。
6. **测试和门禁不可跳过**：状态图、意图短路、契约、权限、脱敏、幂等、SSE 和 HITL 都必须有匹配风险等级的验证；未配置外部能力只能使用 Fake Adapter。
7. **可观测与最小暴露**：全链路携带关联标识，只记录白名单字段与脱敏摘要；禁止记录验证码、Cookie、Token、完整提示词、私有思维链和未经脱敏个人文本。

### 11.4 P0 快速验收顺序

在 Fake Adapter 环境按以下顺序执行验证：

1. 使用预置账号密码建立 Cookie 会话；跨用户访问被安全拒绝；退出或会话过期后受保护资源不可访问。
2. 创建会话和 run，验证 `run_started`；以规则、向量、多意图、未命中和改写样本验证 L0～L3 路径。
4. 验证澄清、Fake 只读查询、候选来源/时间/限制、SSE 重连和状态查询回退。
5. 验证 Fake 审批的批准、拒绝、编辑、超时和重复恢复；验证管理员按关联标识查询脱敏调用链。

### 11.5 未解锁能力的强制边界

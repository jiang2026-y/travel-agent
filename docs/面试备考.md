# 大模型应用开发工程师面试备考（差旅助手 / 汽车领域 RAG）

本文档用于准备以「企业差旅智能助手」与「LLMcopy 汽车领域 RAG 问答」两个项目为主线的技术面试。
内容依次为：简历口径风险与修正、通用叙事模板、两个项目的标准答法与追问答法、
通用高频考点库、十二道送命题速答、面试前自检清单。
文档中的参数、阈值、机制均以两个仓库当前代码和文档为准；凡代码未实现的规划能力，一律不作为已完成能力陈述。

## 一、简历口径风险与修正

### 1.1 必须修正的一条数据陈述

简历中"将召回率由 60% 提升至 90%，准确率由 60% 提升至 85%"目前缺少可复现的评测口径支撑，
仓库现有证据如下：

| 证据文件 | 实际状态 |
| --- | --- |
| `evals/reports/full-rag/full-rag-evaluation.json` | `mode` 为 `mock`，不访问 Elasticsearch / MySQL / Neo4j 与模型 API |
| `evals/reports/ragas-current.json` | 实际评测样本数 `count` 为 3，context_recall 为 1.0 |
| `evals/reports/ragas-baseline.json` | baseline 全部为 `PARTIAL`，因账户欠费 `Arrearage` 导致指标为 null |
| `evals/reports/rag-evaluation-report.md` | 明确写明"未完成真实链路和同配置 RAGAS 评审前，不报告提升百分比" |
| 数据集 | P0 人工脱敏样本 20 条、MinerU 检索样本 30 条、意图对比样本 12 条 |

被追问时最容易暴露的三个问题：数据集规模多大？baseline 与 current 是否为同一数据集、同一配置？
指标口径是 recall@5、MRR 还是 RAGAS 的 context_recall？

推荐改法（二选一）：

1. 补做真实链路评测：固定同一数据集，分别跑 baseline 与 current，再报告提升幅度。
2. 改写简历表述：说明"搭建了 RAGAS 评测框架与 P0 20 条、MinerU 检索 30 条样本集，
   支持 baseline/current 配对评测，真实链路评测待补"。

第二种更安全，也更能体现评测设计能力：主动说明评测边界，比报一个无法复现的数字更可信。

### 1.2 陈述纪律

- 只讲代码里真实存在的机制，规划中的能力要主动标注"未接入/待补"。
- 数字必须能说出统计口径、样本量、对比配置三要素，缺一不说。
- 区分"逻辑模块"与"部署单元"：四个智能体不是四个服务，它们同属 `agent-server` 进程。

## 二、通用叙事模板

任何项目提问都按同一条顺序回答，不要从技术栈开始：

背景与场景 → 系统硬约束 → 整体方案 → 关键决策与取舍 → 可验证证据。

两个项目的硬约束分别是：

- 差旅助手：写操作不可逆，必须人工确认；过程必须可见；外部能力失败必须可降级。
- 汽车领域 RAG：三类主体可见范围不同；答案必须可溯源；越权请求必须拒绝且不泄露资源是否存在。

先说约束，技术选择就变成必然结果；先说技术栈，就变成堆料。

## 三、差旅助手项目备考包

### 3.1 一句话介绍

面向企业差旅场景的多智能体助手：用户用自然语言完成差旅申请与审批、机票火车酒店查询预订、
差旅政策与目的地问答，核心设计目标是写操作可控、过程可观测、失败可降级。

### 3.2 架构标准答法

五个可部署应用服务加两个中间件：

| 单元 | 职责 | 对外暴露 |
| --- | --- | --- |
| `web` | 对话界面、执行时间线、结果卡片、偏好与管理面板 | 是 |
| `api-server` | 会话与 Run 生命周期、差旅单与审批持久化、偏好、审计、SSE 转发 | 是 |
| `agent-server` | LangGraph 编排、四个 Agent、工具实现、记忆与摘要、事件发布 | 仅内网 |
| `tool-gateway` | 模型与工具出口，按模型与 Agent 白名单放行 | 仅内网 |
| `egress-proxy` | Squid 出网代理，默认拒绝，仅放行域名白名单 | 仅内网 |
| PostgreSQL 16 | 会话、消息、差旅单、审批、偏好、审计 | 仅内网 |
| Redis 8 | LangGraph 检查点、确认 Token 哈希、熔断状态、中断广播 | 仅内网 |

`agent-server` 内的四个智能体：master 负责意图理解、子智能体调度、澄清提问与长期记忆读写；
行程管理负责差旅单提交取消修改、冲突检查、审批状态、差旅政策与用户档案；
预订负责途牛机票火车酒店查询下单与取消、用户级 API Key 管理；
信息负责知识库检索、差旅政策、天气、目的地资讯与签证工具。
辅助小模型为 `qwen3.6-flash`（会话标题与推荐追问，温度 0、禁工具、禁思考）与 `glm-5.1`（记忆压缩摘要）。

拆分理由要落在信任边界上：浏览器只能到 `api-server`；`agent-server` 与 `tool-gateway` 不对公网暴露；
Agent 调模型与调第三方 API 必须经 `tool-gateway` 再到 Squid 白名单代理，因此即使提示词注入成功，
也发不出白名单外的请求；内部 Token 与第三方 Key 以 Docker Secret 只读挂载到需要的服务，
浏览器与日志永远看不到明文。代价是多一跳网络往返、超时链路更复杂、跨服务排查依赖 trace_id 与审计事件。

### 3.3 请求链路标准答法（八步）

1. 前端发消息，`api-server` 完成鉴权、创建 Run、写 PostgreSQL，再以内部命令（Bearer Token + 调用链校验）转给 `agent-server`。
2. `agent-server` 执行 L0 → L1 → L2 →（一次改写）→ L3 的意图识别，产出结构化结果。
3. `route_from_recognition` 判定直连派发（`DIRECT_DISPATCH`）还是转澄清（`CLARIFY`）。
4. Master Agent 按意图简报以 ReAct 方式调度子 Agent，最多 15 次迭代。
5. 子 Agent 经 `tool-gateway` 调模型与工具；写类工具触发中断，向用户抛确认卡片。
6. 用户确认后，服务端原子消费确认 Token、校验参数指纹，通过后才执行写操作并落库。
7. 全过程以 SSE 推送 32 类事件，前端渲染为逐条揭示的执行时间线，token 按 24 字符合批。
8. LangGraph 检查点写 Redis，中断与续跑均基于节点边界。

### 3.4 核心机制与追问答法

**三层意图识别**

考点是成本、延迟与可控性的三角权衡：L1 正则零成本高精度但召回有限；L2 向量覆盖广但有误判风险；
L3 大模型最准也最贵。短路流程让多数请求在前两层解决，只有不确定的才付模型费用。
L2 的判定规则：Top-1 分数 ≥ 0.75；若 Top-2 与 Top-1 属于不同 `intent_code` 且分差 ≤ 0.05，
判定为 `ambiguous`。判定对象是意图码而非目标 Agent。判歧义后不再改写，直接进 L3——
改写解决的是用户表达歧义，解决不了检索分不开的问题。
意图种子为 1024 维向量，启动时按每批 10 条灌库，版本必须单一，异常时保留旧索引。
改写最多一次，且明令禁止改动订单号、航班号、日期、金额与地点。

**路由白名单**

模型只能输出目录内的 `intent_code`，且 `target_agent` 必须与目录声明一致，否则 Pydantic 校验失败，
流程回落为 `unknown` 并转澄清。`route_from_recognition` 要求非多意图、置信度为 high、
意图不是 unknown、目标 Agent 不是未接入的 `itineraryPlanAgent`，四条同时满足才直连派发。
契约测试锁定 L3 提示词中的映射表与代码侧意图目录，防止两侧新增或改名不同步。

**写操作人在环确认**

Redis 只保存确认 Token 的 SHA-256 哈希，TTL 900 秒，不保存明文，也不仅存在前端本地。
前端轮询会轮换 Token，服务端对最近一版做宽限，解决"点确认时刚好过期"的竞态。
执行写事务前用 `WATCH/MULTI` 原子消费 Token，并绑定交互 ID 与工具参数指纹，
防止用户确认后参数被替换再执行。用户提交决定后立即摘除展示索引，避免恢复执行期间卡片反复弹出。

**真可中断与断点续跑**

会话级执行注册表记录在途 `asyncio.Task`，同一会话同时只允许一个在途运行；
通过 Redis Pub/Sub 把中断广播到其他节点，并用广播时间戳做时序校验，避免误杀广播后新起的执行流；
取消不写 `failed`，只发布 `interrupted` 事件，检查点停在上一个节点边界，用户继续发消息即可续跑，
发新消息会自动打断上一轮。

**流式输出与过程可视化**

模型侧 SSE 透传，LangGraph `astream` 过滤工具调用增量，按 24 字符合批推送 `token` 事件；
共 32 类 SSE 事件覆盖意图识别、路由、子智能体、工具开始与完成、知识库检索、结果卡片、
Token 用量与中断；前端把本轮事件渲染为逐条揭示的时间线；途牛查询结果渲染为结构化结果卡片，最多 5 条。

**上下文与记忆治理**

工具结果超长列表截断为 10 条并标注省略条数，丢弃模型决策无用字段，折叠过期技能正文；
消息条数 ≥ 60 或估算 token ≥ 98304 触发摘要，保留最近 20 条；
长期记忆按 `user_id` 隔离，未配置记忆库时降级为"无长期记忆"，不影响主流程。

**稳定性与降级**

工具级熔断连续 3 次失败进入 OPEN，冷却 60 秒起指数退避至最多 600 秒，状态放 Redis 供多实例共享，
半开探测成功自动恢复；超时按执行类 600 秒、查询类 5 秒分层；
启动时把超过 24 小时仍处于 `created`、`queued`、`running` 的历史 Run 标记失败并写审计；
上游未配置、401/403、超时、5xx 统一映射为稳定错误码，不透传上游正文。

**安全与合规**

证件、手机号、姓名拼音与消息正文使用 AES-256-GCM 加密存储；内部 Token 与第三方 Key 经 Docker Secret
只读挂载，环境变量只保存文件路径；出网白名单只放行模型、知识库、长期记忆、天气、资讯与签证域名；
日志、工具输出与诊断事件统一脱敏；用户级第三方 API Key 只向界面暴露"是否已配置"。

### 3.5 差旅助手高频追问清单

- 为什么不让 Master 自由路由？（模型输出不可信，写操作不可逆，路由必须可验证）
- 如果 L3 返回白名单外意图会怎样？（Pydantic 校验失败 → 回落 unknown → 转澄清）
- 确认 Token 为什么存哈希而不是明文？（Redis 泄露或误读也不能直接重放写操作）
- 用户重复点击确认怎么办？（`WATCH/MULTI` 原子消费，Token 一次性）
- 中断会不会留下半截写操作？（写事务只在下游原子调用内执行，取消只发 interrupted）
- 上下文超长怎么处理？（工具结果压缩、摘要中间件、长期记忆分层）
- 如何防止提示词注入？（工具与出网白名单、参数指纹、服务端权限校验、输出脱敏）
- 为什么用 LangGraph？（状态机 + Checkpoint + Middleware 天然适配中断恢复与 HITL）

## 四、汽车领域 RAG 项目备考包

### 4.1 一句话介绍

面向汽车领域的受控 RAG 问答系统，同时服务普通顾客、已购车主与企业员工，
三类主体可见范围不同，要求答案可溯源、越权必拒且不泄露资源是否存在。

### 4.2 架构

FastAPI 后端加最小 Next.js 前端；MySQL 存主体身份、权限、会话、文档元数据与分段；
Elasticsearch 的 `know-engine` 索引同时承载向量与中文全文检索
（`text-embedding-v4`，1536 维，余弦相似度，`int8_hnsw`）；
MinIO 存原始文件、Markdown 与图片；Redis 管分布式锁与会话；Neo4j 承载车辆关系数据；
MinerU 负责云端文档解析。

### 4.3 文档到知识库链路

上传返回 202 与 `task_id` → 原文存 MinIO → MinerU 解析为 Markdown 与图片 → 按 Markdown 标题层级
（`#` 至 `######`）做父子切分（1000 字符、100 字符重叠）→ 超长标题段同时保存完整父块
（`skip_embedding=1`）与可检索子块（元数据含 `parentChunkId`）→ 写入分段表 → 领导审核 →
审核通过才向量化 → 重新向量化先删除该文档旧向量 → 回填向量 ID 与 `VECTOR_STORED` 状态。

这一链路最值得强调的一句话：审核通过才向量化，且重新向量化先清旧向量，
因此检索侧永远不会命中未发布内容。

### 4.4 检索链路

意图识别 → 查询改写 → 查询路由 → 向量与全文双路召回 → RRF 融合 →
`qwen3-rerank` 重排取 Top5 → MySQL 二次授权校验 → 父子上下文回补。

关键点是权限校验内嵌在检索链路里，不依赖模型自行判断可见性：
短父块整块补回，长父块按相邻子块窗口补全。

### 4.5 服务可靠性

Redis 分布式锁键名为 `llmcopy:lock:{scene}:{key}`，使用随机令牌 + Lua 比对删除，并在租期内自动续租；
同一用户并发上传立即返回 409；Elasticsearch 或 Redis 不可用时返回 503，
不接受"无锁当成成功"式的静默降级；SSE 六类事件配 15 秒心跳与 120 秒上限，
单主体同时只允许一条回答流，断连即取消上游模型调用，且不落库任何部分回答。

### 4.6 汽车领域 RAG 高频追问清单

- 为什么用 RRF 而不是加权求和分数？（不同召回器分数量纲不可比，RRF 只用排名，鲁棒且免调参）
- 为什么做父子切分？（检索用小块保证语义聚焦，生成用父块保证上下文完整）
- 为什么 rerank 只取 Top5？（重排成本与上下文窗口的折中）
- 权限为什么放在 MySQL 二次校验？（可见性是确定性规则，不能交给概率模型）
- 为什么用 Lua 比对删除？（防止任务超时后误删他人持有的锁）
- 为什么 409 / 503 而不是降级？（企业知识库宁可不服务，也不能返回错误数据）
- 断线后为什么不落库部分回答？（避免半截答案进入会话历史与评测集）
- embedding 维度与索引参数怎么定的？（1536 维、余弦、`int8_hnsw`，在内存占用与召回精度间取平衡）

## 五、高频考点库

### 5.1 检索与 RAG

- 切分策略：固定长度、按标题层级、语义切分各自的适用场景；重叠区的作用是保住跨块语义连续性。
- 向量检索：余弦相似度与点积在归一化后等价；HNSW 是近似最近邻图索引，
  `ef_search` 越大召回越高、延迟越高；`int8` 量化省内存但引入精度损失。
- 混合检索：向量召回负责语义泛化，全文召回负责专有名词与编号精确匹配，两者互补。
- RRF 融合公式：对每个文档累加 `1 / (k + rank_i)`，`k` 常取 60，只用排名，不依赖分数分布。
- 重排：rerank 模型比 embedding 更贵更准，因此只对召回 TopN 做精排，取 TopK 进上下文。
- 幻觉治理：引用溯源、上下文回补、无答案兜底、生成温度 0、答案与引用同时落库。
- 上下文窗口：过长会导致中间信息被忽略（lost in the middle），需要压缩与按需回补。
- 未发布内容隔离：审核通过才向量化，重新向量化先删旧向量。

### 5.2 Agent 与编排

- ReAct 与工具调用：ReAct 是"推理—行动—观察"循环，现代实现以 function calling 落地。
- 多智能体的拆分依据：工具集独立、上下文隔离、权限与风险等级不同，而不是按人数分摊。
- LangGraph 三件套：StateGraph 定义状态与转移，Checkpoint 支持持久化与断点续跑，
  Middleware 承载压缩、熔断、工具错误与人在环中断。
- 路由可控性：模型只输出受校验的结构化结论，路由目标由服务端白名单决定。
- 上下文管理：工具结果压缩、历史摘要、长期记忆分层，三者解决不同时间尺度的信息。
- 工具设计：幂等键、只读与写操作区分、参数白名单、默认拒绝、失败可重试。

### 5.3 流式与可靠性

- SSE 与 WebSocket 的选择：单向推送用 SSE，实现简单、天然支持断线重连语义；
  需要双向实时交互才用 WebSocket。
- 首字延迟与吞吐：按字符或固定长度合批推送，兼顾流畅度与事件数量。
- 超时分层：执行类与查询类操作应设置不同超时，避免长任务拖垮短查询。
- 熔断三态：CLOSED / OPEN / HALF_OPEN，状态需多实例共享，冷却时间指数退避。
- 幂等：写操作透传幂等键，服务端以 Token 或键做一次性消费。
- 僵死任务治理：启动时扫描超时未完成状态并标记失败，写审计，避免状态永久悬挂。

### 5.4 安全与合规

- 提示词注入防护要分层：输入不可信、工具与出网白名单、参数约束、输出脱敏、权限服务端校验。
- 敏感信息存储：字段级加密（AES-256-GCM）、密钥与代码分离、Secret 只读挂载。
- 越权设计：不泄露资源是否存在，错误口径统一。
- 审计：谁在什么时候调用了什么工具、传入什么参数摘要、结果如何，全部落库。
- 凭据最小暴露：前端只展示"是否已配置"，日志与事件统一脱敏。

### 5.5 评测与指标

- 检索指标：recall@k、MRR、命中率；生成指标：RAGAS 的 context precision/recall、
  faithfulness、answer relevancy、factual correctness。
- 评测纪律：baseline 与 current 必须同数据集、同配置配对；样本量、失败样本处理规则要写清；
  失败或跳过的样本不能计入平均分。
- 线上指标：点赞点踩、追问率、无答案率、P95 首字延迟、单次会话 token 成本。
- 意图识别评测：整体准确率、相关准确率、实体抽取准确率与 micro-F1。
- 常见追问：为什么不用人工打分？为什么样本这么少？如何避免评测集与线上分布偏移？

### 5.6 成本与性能

- 模型分层：小模型承担标题、推荐、摘要等简单任务，大模型只做决策与生成。
- 短路与缓存：能靠规则和检索解决的问题不要进大模型；命中缓存直接返回。
- 上下文压缩：工具结果截断、历史摘要、按需回补，是降本最直接的手段。
- 批处理：embedding 与 rerank 尽量合批，单请求条数设上限。
- 容量问题：QPS 增长优先考虑无状态服务水平扩展、集中式状态（Redis / 数据库）的瓶颈拆分，
  再看限流、队列与索引分片。

### 5.7 系统设计常见题

- 设计一个多轮对话的记忆系统：短期上下文、会话摘要、长期偏好三层，各自的读写时机与失效策略。
- 设计一套写操作确认机制：Token 生命周期、一次性消费、参数绑定、并发与重放防护。
- 设计一个 RAG 评测体系：数据集构造、baseline 定义、指标选择、回归门禁。
- 设计多租户权限问答：权限在哪里校验、如何做到不泄露资源存在性、如何防止缓存越权。
- 如何做灰度与降级：开关粒度、降级后的用户可见行为、可观测指标与回滚条件。

### 5.8 行为面与软技能

- 你最得意的技术判断是什么？要给出"当时有哪些选项、你为什么选它、结果如何"。
- 最大的失误是什么？要给出补救动作与后续机制改进。
- 与产品或其他角色有分歧时怎么推进？用约束与数据说话，而不是用技术偏好。
- 时间与优先级管理：如何在有限时间内决定做 A 不做 B。
- 反问环节可问：团队的模型选型决策权在哪、评测体系如何建设、上线节奏与回滚机制。

## 六、十二道送命题速答

1. 你怎么证明方案有效？——给评测口径、样本量与对比配置；没有数据就明说待补。
2. 这个指标怎么测的？——先说数据集与配置，再说指标定义，最后说结论。
3. 模型返回非法 JSON 怎么办？——结构化输出 + Pydantic 严格校验 + 失败回落 unknown，不伪造命中。
4. 用户确认后参数变了怎么办？——确认 Token 绑定交互 ID 与参数指纹，指纹不符即拒绝执行。
5. 重复提交或并发点击怎么办？——Token 一次性原子消费，写操作透传幂等键。
6. 上下文超长怎么办？——工具结果截断、历史摘要、长期记忆分层，按需回补。
7. 怎么防提示词注入？——白名单工具与出网、参数约束、服务端权限校验、输出脱敏。
8. 为什么不用微调？——知识时效与权限频繁变化适合检索增强，微调成本高且难以及时回滚。
9. 为什么用 LangGraph 而不是自己写状态机？——检查点、中断恢复与人在环是成熟能力，自研风险更高。
10. 服务挂了怎么办？——超时分层、熔断、降级、幂等重试、僵死任务清理与审计。
11. QPS 涨十倍怎么办？——无状态水平扩展，识别 Redis 与数据库瓶颈，限流削峰，索引分片。
12. 你的最大技术判断失误是什么？——给真实例子加改进机制，不要答"没有"。
